# GitHub Issue와 작업 목표 동기화

Studio가 실행되는 동안 작업실 창을 닫아도 호스트의 동기화 스레드가 등록된 저장소를 확인합니다. 꺼진 호스트는 다음 기동 때 GitHub에 다시 접속해 현재 상태와 이슈 이력을 대조합니다. 저장소 연결과 App 키는 호스트 운영자가 준비합니다. [연결 및 인증 설정](github-connections.md)

## 작업을 시작하는 조건

같은 OS 계정에서 기존 서비스와 설치판의 별도 Studio를 함께 쓰는 경우, 자동 접수를 처음 설정한 저널이 해당 저장소를 담당합니다. 화면을 다시 연결하거나 앱을 재시작해도 이 소유권은 유지됩니다. 서로 다른 컴퓨터나 OS 계정에 같은 GitHub App을 배포할 때는 연결 JSON의 `owner_journal`에 자동 실행을 담당할 Studio의 저널 ID(32자리)를 명시하고 모든 호스트에서 같은 값을 사용하세요. 다른 호스트는 읽기 용도로 연결할 수 있습니다. 호스트 간 인계 시에는 원래 저널과 연결을 함께 이전해 진행 중인 작업 및 게시 이력을 보존하세요.

작업실에는 연결, 숫자 저장소 ID, 브랜치와 허용 폴더를 등록합니다. 자동 실행은 기본적으로 꺼져 있습니다. 켜려면 권한이 있는 GitHub App 연결과 라벨을 붙일 수 있는 사람의 숫자 사용자 ID를 지정합니다. 서로 다른 GitHub 호스트의 같은 번호는 다른 이슈입니다. Studio는 정규 인스턴스 주소, 숫자 저장소 ID, 숫자 이슈 ID의 조합에 목표 하나를 연결합니다. 저장소 이름과 이슈 번호는 조회 경로에 사용합니다.

동기화는 새 작업을 맡기기 전에 현재 이슈, 현재 라벨(기본값 `office:ready`)과 마지막 라벨 추가·제거 기록을 읽습니다. 해당 라벨을 마지막으로 추가한 사람의 숫자 ID가 허용 목록에 있어야 하며 현재도 같은 계정에 저장소 쓰기 권한이 있어야 합니다. App 자신이나 다른 봇이 붙인 라벨로 작업을 시작할 수 없습니다. PC가 꺼진 사이에 닫힌 이슈나 라벨이 사라진 이슈는 실행 대기열에 넣지 않습니다.

접수 시 제목·본문(완료 조건과 링크 포함), 원문 지문, 본문 바이트 수와 기준 커밋을 기록합니다. 기록할 때 자격 증명 형식의 문자열을 가립니다. 긴 본문은 전체 지문으로 변경을 판단합니다. 작업실의 조정자가 등록된 폴더와 검증 정책을 적용해 목표를 시작합니다. 각 실행 ID와 외부 목표 ID를 로컬 기록에서 확인할 수 있습니다.

| 관찰한 변화 | 처리 |
| --- | --- |
| 이슈 제목·본문 수정 | 변경 이벤트를 기록합니다. 앞뒤 공백을 제외한 내용이 달라지면 기존 범위와 새 범위를 작업실에 제시합니다. 운영자가 수락하면 진행 중인 작업자에게 지시를 전달합니다. 이미 종료된 작업은 명시적 재시작을 기다립니다. |
| 일반 댓글 | 실행 명령으로 사용하지 않습니다. |
| 진행 중인 질문에 대한 답변 | `/office answer 목표ID 질문ID 답변` 형식으로 연결된 이슈에 작성합니다. 질문 생성 이후의 댓글, 정확한 목표와 질문, 해당 질문 종류에 허용된 사람의 ID를 확인합니다. 편집된 댓글과 봇의 답변은 처리하지 않습니다. 기술 답변과 제품 결정의 허용 목록은 별개입니다. 권한 요청은 작업실에서 처리합니다. |
| 이슈 종료, 연결한 PR 종료·병합 | 로컬 실행과 대기 중인 후속 작업을 정리합니다. 병합하거나 배포하는 기능은 없습니다. |
| 이슈 다시 열기 | 작업실의 재시작 동작으로 새 실행을 요청해야 합니다. 이전 목표 ID를 보존하고 새 실행 ID와 세대별 후보 브랜치를 사용합니다. |
| 일시적인 조회·게시 실패 | 안전한 오류 코드를 표시합니다. 요청 제한은 같은 설치의 다음 동기화에도 적용됩니다. 게시 장애 때문에 코드 작업을 다시 시작하지 않습니다. |

## PR과 CI

작업실 설정에서 초안 PR 게시를 켤 수 있습니다. 독립 검토와 로컬 검증을 통과한 후보만 게시하며, 게시 전에 이슈와 라벨 권한을 다시 확인합니다. 기존 PR을 연결할 때는 같은 저장소·대상 브랜치인지 확인하고 PR의 커밋 트리와 작업실에서 검증한 후보 트리를 대조합니다. 연결한 PR이 수동 관리 브랜치에 있으면 후속 로컬 후보를 운영자가 게시하고 새 커밋을 검증해 다시 연결할 수 있습니다.

체크 이름, 결론과 커밋을 이벤트로 기록합니다. 자동 수정은 지정한 이름의 GitHub Actions 체크에서 검증된 현재 PR head의 단위 테스트 실패 근거가 있을 때만 가능합니다. 취소·시간 초과·실행기 장애, 출처나 원인이 불명확한 실패 및 이전 커밋 결과는 기록만 합니다. 같은 head의 오래된 실패가 이후 성공으로 대체되면 재작업을 시작하지 않습니다. CI 재작업은 세대별 설정 한도(기본 0회, 최대 3회) 안에서 같은 head에 한 번만 시작합니다. 재작업 직전에 이슈 상태, 라벨 적용 권한과 PR head를 다시 읽습니다.

변경 요청 리뷰도 연결한 PR의 현재 검증된 커밋에 대한 것이어야 합니다. 작업 시작 허용 목록에 있고 저장소에 쓰기 권한이 있는 사람의 최신 유효한 변경 요청만 같은 외부 목표의 후속 작업으로 전달합니다. 같은 리뷰 ID와 커밋의 요청은 한 번만 적용합니다.

## 중복 방지와 게시 복구

SQLite에 현재 연결, 조회 위치, 접수한 요청, 목표·실행·PR 매핑, 게시 의도와 이벤트를 기록합니다. 같은 저널의 수동 요청과 백그라운드 동기화는 저장소별 OS 잠금을 공유합니다. 실행 요청을 저장한 뒤 조정자를 호출하며, 중간에 호스트가 멈추면 기록된 실행 ID로 기존 접수 결과를 대조합니다. 자동 실행이 꺼진 연결은 관찰 상태만 기록합니다.

기본 조회 주기는 90초입니다. 수동 동기화는 백그라운드 큐를 깨웁니다. 한 번에 최대 두 쪽의 이슈 목록을 읽고 최근 확인 시각이 오래된 이슈부터 최대 25건을 대조합니다. 페이지 처리 중 재시작하면 저장한 쪽 번호와 같은 조회 시작 시각으로 이어갑니다. 증분 조회는 5초를 겹쳐 읽고 한 시간마다 전체 조회를 다시 시작합니다. 연결된 PR과 진행 중인 이슈는 라벨 목록에서 사라져도 추적합니다.

GitHub에는 목표 ID, 상태·담당·시도, 검증 집계와 남은 수동 확인, 공개할 수 있는 질문·답변 형식, 연결된 PR 번호를 하나의 상태 댓글에 갱신합니다. 작업실의 로컬 파일 경로와 검증 로그는 댓글에 싣지 않습니다. 댓글의 숨은 마커와 App 작성자 신원이 모두 일치해야 갱신합니다. 생성 응답을 잃으면 전체 댓글 목록에서 마커를 찾아 기존 댓글을 채택합니다. 마커가 계속 보이지 않으면 자동 재게시를 보류합니다. 운영자가 실제 이슈를 확인하고 **게시 재시도**를 선택하면 마커를 한 번 더 확인한 뒤 재시도 의도를 기록합니다. 이 과정에서도 새로운 코드 실행을 만들지 않습니다.
