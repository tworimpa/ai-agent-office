## 개정 2 (2026-11-27) — 엔진과 `gh` 에 대한 소유자 결정

| 소유자 결정 | 뜻 | 이 문서에서 바뀐 것 |
| --- | --- | --- |
| `agy` 는 구현만 하고 가능하면 Codex를 활용한다 | Antigravity 어댑터와 선택지는 유지한다. 기본값과 새로 만드는 기능은 Codex를 먼저 쓴다 | 결정 ① 확정. 아래 "엔진 기본값 변경" |
| 시스템에 로그인된 `gh` 를 사용한다 | GitHub 작업은 이 PC의 `gh` 로그인을 쓴다. 개인 사용 흐름에서 GitHub App 연결을 요구하지 않는다 | 12장의 전제 확정. 14장 B5의 트리거와 답장도 같은 `gh` 로그인을 쓴다 |

**엔진 기본값 변경 (초판 P0-1을 대체).** 작은 변경이지만 기존 기록의 해석이 걸려 있어 주의가 필요하다.

- 바꿀 것: 기본 리뷰어를 `antigravity` 에서 `codex` 로. 개발자와 리뷰어가 같은 엔진이어도 되는지 확인했다 — 코드에 같은 엔진을 막는 검사는 없고, 리뷰어는 별도 프로세스·별도 세션으로 읽기 전용 호출된다. 독립성은 엔진이 아니라 세션 분리와 호스트가 실행한 테스트 결과에서 나온다.
- **주의: 상수를 그냥 바꾸면 안 된다.** `DEFAULT_DEVELOPER`/`DEFAULT_REVIEWER` 는 "새 실행의 기본값"과 "엔진이 기록되지 않은 옛 실행의 해석" 두 용도로 함께 쓰인다(`studio_runner.py:61`, `team_wire.py:127-128`, `studio_server.py:535-536`). 값을 바꾸면 옛 실행의 리뷰어가 Codex였던 것처럼 읽히고, 같은 요청의 재전송 대조가 어긋난다. 옛 기록용 상수(예: `LEGACY_REVIEWER = "antigravity"`)를 분리하고 새 기본값만 바꾼다.
- 같이 고칠 곳: `engines.py` (`INITIAL_ENGINES` 는 진단·`doctor --require` 의 기본 대상이다. `("codex",)` 로 줄이면 `agy` 가 없어도 `doctor` 가 통과한다), `AGENTS.md` 와 `docs/engines.md`·README의 "Codex + Antigravity" 초기 프로필 문구, 기본 리뷰어를 가정한 테스트(해당 파일 16개).
- 새로 만드는 기능의 엔진: 14장의 봇 세션(B1), 봇 기억 정리(B2), 일정 실행(B5)은 Codex를 기본으로 설계하고 먼저 Codex로 검증한다. Codex는 쓰기 가능 경로 설정(`codex_inbox.py:342`)과 같은 스레드로 턴을 잇는 app-server 연결이 이미 구현돼 있어 봇 홈 방식에 가장 잘 맞는다. `agy` 는 선택하면 동작하도록 어댑터만 맞춘다.
- 완료 기준: 새 Workspace와 CLI `run` 의 기본 리뷰어가 Codex다. 엔진이 기록되지 않은 옛 실행을 열면 여전히 Antigravity로 표시된다(회귀 테스트). `agy` 를 직접 고른 실행은 지금처럼 돈다.
- 약관 위험(M-1)의 처리: 기본 경로에서 `agy` 가 빠지므로 추가 경고 화면은 만들지 않는다. `docs/engines.md` 에 한 문단으로 적어 둔다.

**`gh` 확인.** 이 PC에서 `gh` 2.95.0이 설치돼 있고 `gh auth status` 가 종료 코드 0을 돌려준다(2026-11-27). 12장 0단계의 준비 확인이 통과하는 상태다.

**결정 ⑩에 대한 해석.** "시스템에 로그인된 `gh` 사용"은 누구의 자격증명으로 GitHub에 접근하는지를 정한 것으로 읽었다. 봇 세션이 `gh` 를 직접 부를지, 호스트가 대신 부를지는 14장의 권고(호스트가 대신 실행하고 기록)대로 둔다. 어느 쪽이든 쓰는 로그인은 같다. 소유자가 "봇이 직접 `gh` 를 쓴다"는 뜻이었다면 14장 "봇이 호스트에 부탁하는 방법"의 `github` 요청 종류를 없애고 봇 세션 환경에서 `gh` 차단을 푸는 것으로 바꾸면 된다.

## 개정 3 (2026-11-27) — 남은 결정 세 가지

| 소유자 결정 | 반영 |
| --- | --- |
| 실제 엔진 시험을 승인한다 | 14장 "먼저 확인할 것"의 세 가지를 Codex로 시험할 수 있다. 일회용 저장소와 일회용 봇 홈에서만 하고, 실행 ID와 결과를 문서에 남긴다. 승인 범위는 이 시험과 각 단계 끝의 실검증(P0-8)이다 |
| Rust 비교판을 보관한다 | 문서 수준 보관은 이 문서와 같은 PR에서 했다: README 상단 안내를 내리고 `docs/rust-comparison.md` 에 보관 표시. **CI·릴리스에서 빼는 일은 아직 하지 않았다** — 아래 "Rust 비교판 검사 제거의 범위" 참조 |
| 호스트 푸시를 결정 기록에 명시한다 | `docs/decisions.md` 에 ADR-007(호스트의 `gh` 반영), ADR-008(엔진 선호), ADR-009(Rust 비교판 보관), ADR-010(봇 방향과 개인 사용 우선)을 추가했다 |

**Rust 비교판 검사 제거의 범위 — 소유자의 명시적 승인이 따로 필요하다.**
Rust 비교판 검사는 CI 워크플로 하나가 아니라 릴리스와 배포의 신뢰 판단에 들어가 있다.

| 위치 | 하는 일 |
| --- | --- |
| `.github/workflows/desktop.yml:164-166` | `desktop` 작업 뒤에 `rust-comparison.yml` 을 재사용 워크플로로 호출 |
| `scripts/desktop_release.py:29` | 릴리스 전에 통과해야 하는 검사 목록에 `rust-comparison / <OS> / Rust comparison` 포함 |
| `src/agent_office/policy_github.py:19-24, 157, 246-251` | 운영자 자동 배포가 신뢰하는 검사 집합과 워크플로 파일 목록에 포함. 다른 재사용 워크플로는 "unknown reusable workflow"로 거절 |
| `scripts/split-session-bootstrap.ps1:33` | 분리 세션 부트스트랩이 기대하는 검증 참조 |
| `tests/test_policy_github.py` | 위 정책의 테스트 |

이 목록에서 Rust 검사를 빼는 것은 **릴리스 게이트와 배포 신뢰 정책을 바꾸는 일**이다. `AGENTS.md` 는 보안 정책 변경에 명시적 승인을 요구한다. "보관" 결정이 이 범위까지 포함하는지 확인을 받은 뒤 별도 PR로 한다. 그때까지 PR마다 Rust 비교판 빌드는 계속 돈다.

**기본 리뷰어 전환도 별도 PR로 한다.** 개정 2에 적은 대로 기본값 상수가 요청 해시(`studio_runner.py:61`)와 Studio 간 전송 기본값(`team_wire.py:127-128`, `studio_server.py:535-536`)에 쓰이므로 옛 기록용 상수를 분리하는 작업과 전체 테스트가 필요하다. 그 PR이 병합되기 전까지 코드의 기본 리뷰어는 Antigravity이고, `AGENTS.md` 의 초기 프로필 문구도 그때 함께 고친다.

**이제 남은 결정은 하나다.** Rust 비교판 검사를 릴리스 게이트와 배포 신뢰 정책에서 빼도 되는가.

## 개정 4 (2026-11-27) — Codex 사전 시험 결과

개정 3의 승인에 따라 14장 "먼저 확인할 것"을 실제 Codex로 시험했다. 일회용 Git 저장소와 일회용 봇 홈에서만 했고, 이 저장소와 실행 중인 Studio는 건드리지 않았다.

- 환경: Windows 11 네이티브, 시스템에 설치된 Codex CLI 0.172.0, 소유자의 기존 로그인
- 호출: `codex exec --json --sandbox workspace-write --skip-git-repo-check -C <봇 홈>` 로 첫 턴, `codex exec … resume <세션 ID>` 로 둘째 턴. 세션 ID `01a21d24-9313-7922-8746-38fd59f8361e`
- 봇 홈에는 `AGENTS.md`(정체, 저장소 경로와 "읽기만", 요청 파일 형식), `SOUL.md`, 빈 `MEMORY.md` 를 두었다
- 모델 호출 3회(70초, 28초, 3초 만에 충돌)

| 확인한 것 | 결과 | 근거 |
| --- | --- | --- |
| 봇 홈에서 저장소 파일 읽기 | 됨 | 저장소의 `inventory.txt` 값 4821을 정확히 답함 |
| 스스로 기억 쓰기 | 됨 | `MEMORY.md` 에 "The project codename is heron-7." 한 줄 추가 |
| 요청 파일로 워커 위임 부탁 | 됨 | `requests/4519ed9d.json` 생성. 유효한 JSON, 지정한 키 네 개만, 파일 이름과 `id` 일치. 저장소는 건드리지 않음 |
| 세션 재개로 대화 잇기 | 됨 | 둘째 턴이 같은 스레드 ID로 돌았고, 어떤 파일에도 쓰지 않은 "세션 단어"를 기억함 |
| **저장소에 쓰지 못하게 막기** | **안 됨** | 둘째 턴에서 허락을 받고 저장소에 빈 파일을 만들어 보게 했더니 `workspace-write` 샌드박스인데도 **파일이 만들어졌다** |
| Windows 샌드박스 백엔드(`-c windows.sandbox=mxc`)로 다시 | 시험 불가 | 시스템 Codex가 3초 만에 종료 코드 139로 충돌 |

**설계에 주는 영향.**

1. **14장의 기본 구조는 Codex에서 성립한다.** 홈 폴더, 스스로 쓰는 기억, 요청 파일, 세션 재개 모두 추가 장치 없이 동작했다. 요청 파일 방식을 기본으로 한다는 권고를 유지한다.
2. **"봇은 저장소를 읽기만 한다"를 엔진 샌드박스에 맡길 수 없다.** 적어도 Windows 네이티브의 시스템 Codex에서는 프롬프트의 지시만이 막고 있었다. 호스트가 보장해야 한다. 권고: 봇 세션에는 원본 체크아웃이 아니라 **그 턴을 위해 만든 읽기용 작업 트리**를 준다(실행마다 worktree를 만드는 지금의 방식과 같다). 봇이 거기에 무엇을 쓰든 원본에는 닿지 않고, 턴이 끝나면 호스트가 변경 여부를 기록하고 버린다. B1의 설계에 이 항목을 넣는다.
3. **같은 한계가 기존 워커에도 있을 수 있다.** 이번 시험은 봇 홈 구성에서만 했고 워커 경로는 시험하지 않았다. 다만 워커도 같은 `--sandbox workspace-write` 를 쓴다(`adapters.py:61-64`). Windows 네이티브에서 pip로 띄운 Studio라면 워커가 worktree 밖에 쓸 수 있다고 보고 다뤄야 한다. README의 기존 경고("On Windows, validate Codex's effective native sandbox before using `--allow-edits`")가 가리키던 바로 그 문제다. 설치판은 내장 Codex와 MXC 백엔드를 쓰는데(`engines.py:23-27`) 그 경로는 이번에 시험하지 않았다.
4. **봇 세션은 소유자의 전역 Codex 설정을 물려받는다.** 시험 중 전역 설정의 MCP 서버(로컬 주소)에 붙으려다 실패했다는 오류가 표준 오류에 반복 출력됐다. 봇 세션에서 전역 MCP 서버와 설정을 그대로 쓸지, 봇별로 격리할지 정해야 한다.

**시험하지 않은 것.** WSL·Linux에서의 샌드박스 동작, `agy`, app-server 방식의 스레드 연결, 긴 대화에서의 재개, 요청 파일 형식이 틀렸을 때의 복구. 시험 산출물은 세션 임시 폴더에 있어 보존되지 않는다. 위 표의 값이 기록의 전부다.

## 0. 이 문서를 읽는 법

**근거 표기.** `파일:줄` 은 기준 커밋에서 직접 열어 확인한 위치다. "실행 확인"은 격리된 임시 DB와 임시 포트로 Studio를 띄워 화면을 본 결과다. "외부 조사"는 2026-11-27에 `gh api` 와 공개 웹 페이지에서 읽은 값이며 출처를 부록 C에 모았다.

**신뢰도.** 각 진단에 `확실` / `보통` / `재확인 필요` 를 붙였다. `재확인 필요` 는 2차 출처에 의존했거나 확인 범위가 좁은 항목이다. 후속 작업 전에 해당 줄의 근거를 다시 확인할 것.

**이 문서가 하지 않은 것.** 유료 모델 호출이 생기는 실제 작업 의뢰는 하지 않았다. 그래서 "작업 결과 검토 화면"은 코드와 문서로만 평가했다. 전체 pytest도 돌리지 않았고 CI 기록으로 대신했다. 자세한 한계는 11장에 있다.

**용어.** 이 저장소는 같은 대상을 여러 이름으로 부른다(그 자체가 진단 U-2다). 이 문서에서는 아래 이름으로 통일한다.

| 이 문서의 용어 | 뜻 | 저장소에서 섞여 쓰이는 이름 |
| --- | --- | --- |
| Studio | 로컬 HTTP 서버와 웹 화면 전체 | 작업실, 로컬 작업실, Office |
| Workspace | 등록한 폴더 묶음과 그 설정 | 작업공간, 작업실, 프로젝트 작업실 |
| 실행(run) | 의뢰 한 건의 처리 단위. 별도 Git worktree를 가진다 | 작업, 실행, 작업 기록 |
| 엔진 | 워커로 호출하는 외부 코딩 CLI | Codex, Antigravity(`agy`), Claude Code, Gemini CLI, Cline |
| 실행 자리 | 파이프라인이 호출하는 고정 역할 3개 | coordinator/developer/reviewer, 조정자/개발자/리뷰어, 담당자/검토자, 개발 담당/검토 담당 |
| 봇 | 이름·역할·지침 파일 묶음(Bot Definition 1.0) | 봇, 캐릭터, 멤버 |
| 왕명 | 여러 봇에게 한 번에 일을 나눠 주는 의뢰 | 왕명, 어명, 왕의 어명 |
| 장시간 목표 | 반복 수정·검증을 예산 안에서 이어 가는 실행 | 밤샘 목표, 야간 목표, 장시간 개발 목표, overnight goal |

## 1. 결론

**한 줄 판정.** 엔지니어링 규율은 높고 기능 폭은 넓지만, 제품으로서는 아직 "소유자 한 사람이 자기 저장소를 개발하는 데 쓰는 도구"다. 처음 설치한 다른 개발자가 값을 얻기 어렵고, 시장에는 같은 문제를 훨씬 큰 규모로 푸는 무료 경쟁 제품이 이미 있다.

**점수(5점 만점, 근거는 3~6장).**

| 항목 | 점수 | 한 줄 이유 |
| --- | --- | --- |
| 엔지니어링 규율(테스트·증거·실패 시 닫힘) | 4.0 | pytest 1,331건, Windows/Linux CI, 설치·업그레이드 검증, 근거 중심 기록 |
| 기능 폭 | 4.0 | 계획 승인, 요청함, 부재중 위임, 원격 호스트, GitHub 연동, 장시간 목표, 봇 공유까지 3주 만에 구현 |
| 사용성(설치→첫 결과→반영) | 2.5 | 첫 화면은 단순하나 화면 체계가 둘로 갈라져 있고, 결과를 내 저장소에 반영하는 길이 없다 |
| 봇 확장성 | 2.0 | 봇은 프롬프트에 붙는 텍스트다. 도구·트리거·기억 갱신·봇별 엔진이 없다 |
| 엔진 확장성 | 2.0 | 엔진 5개가 분기문으로 고정돼 있고 추가 지점이 15개 파일에 흩어져 있다 |
| 실사용 검증 | 2.0 | 인증된 실제 CLI로 확인한 것은 대부분 읽기 전용. 수정 모드 실검증 기록은 1건 |
| 상품성·시장 준비 | 1.5 | 별 0개, 설치 파일 미서명, 자동 업데이트 없음, README에 화면 한 장 없음, 기본 엔진 조합에 약관 위험 |

**가장 무거운 문제 다섯 가지.**

1. **기본 엔진 조합이 공급자 약관과 충돌할 수 있다.** 기본 리뷰어는 Antigravity(`agy`)다. Google의 Antigravity FAQ는 `agy` 를 서드파티 에이전트나 앱이 감싸 호출하는 것을 "소비자 요금제에서 지원하지 않는다"고 적고, 포럼의 운영 측 답변(2026-10-16, 2026-11-20)도 같은 취지다. 제품의 기본값이 사용자 계정을 위험에 놓을 수 있다. → 진단 M-1, 조치 P0-1
2. **결과를 사용자 저장소에 반영하는 길이 제품 안에 없다.** 실행 결과는 `ao/task-<id>` 브랜치의 worktree에 남는다. "채택"은 기록만 남기고(`overnight_goals.py:233-264`), PR 초안 게시는 GitHub App 연결을 설정한 경우에만 된다. 이 PC에도 정리되지 않은 `ao/task-*` worktree가 12개 남아 있다. → U-4, P0-2
3. **Studio의 일반 수정 실행은 pytest 전용이다.** 테스트 명령이 `python -m pytest -q` 로 고정돼 있어(`studio_runner.py:634-635`) Python이 아닌 저장소에서는 테스트 단계가 실패로 끝난다. 임의의 사용자 프로젝트에 쓸 수 있는 범위가 좁다. → U-7, P0-3
4. **봇이 "지침 텍스트" 이상이 아니다.** 실행 시 봇은 지침과 `.md`·`.txt` 파일을 JSON으로 프롬프트 앞에 붙인 것이 전부다(`goal_workers.py:226-250`). 도구(MCP), 일정·이벤트 트리거, 스스로 갱신하는 기억, 봇별 엔진 지정, 봇 사이의 인계가 없다. 벤치마크인 Orca의 봇은 이 다섯 가지를 모두 갖고 있다. → 4장, P1-1~P1-6
5. **배포 신뢰와 발견 가능성이 0에 가깝다.** 공개 저장소지만 설명·토픽이 비어 있고 별 0개, 릴리스 자산 다운로드는 한 자릿수다. 설치 파일은 서명되지 않았고 자동 업데이트가 없다. README에는 스크린샷이 없다. 가장 눈에 띄는 자산(조선 시대 서재 화풍의 회의실)이 저장소 어디에도 보이지 않는다. → 6장, P0-4, P0-6

**지켜야 할 강점 세 가지.**

- **검증하고 나서 보고하는 구조.** 테스트 실행 → 독립 리뷰 → 사람 검토 순서, 알 수 없는 판정은 실패로 처리, 질문과 권한 요청의 구분, 부재중 대리 답변의 근거 기록. 경쟁 제품 다수가 권한 확인 생략(YOLO)을 기본으로 두는 것과 정반대의 방향이다.
- **봇 정의의 엄밀함.** 스키마, 적합성 테스트, 커밋과 해시로 고정한 설치, 충돌 검사가 있는 업데이트와 오프라인 롤백. 기능은 적지만 있는 것은 단단하다.
- **화면의 개성.** 조선 시대 서재, 걸어 다니는 캐릭터, 왕의 책상. 시각 메타포는 Pixel Agents(별 약 1만, 마켓 설치 약 14.8만)에서 채택에 도움이 된다는 것이 확인됐다.

**권고 방향.** 기능 폭으로 Orca와 겨루지 말 것. "검증 근거가 붙은 무인 실행"을 제품의 핵심으로 좁히고, 첫 사용자가 설치부터 결과 반영까지 막히지 않게 만드는 일(P0)을 봇 기능 확장(P1)보다 먼저 할 것. 자세한 선택지는 7장, 작업 목록은 8장.

## 3. 사용성 진단

실행 확인은 임시 DB와 포트 18766으로 띄운 Studio에서 했다. 임시 Git 저장소를 Workspace로 등록하고 봇 하나를 만들었으며, 작업 의뢰는 보내지 않았다.

### 잘 된 점

- **첫 화면의 다음 행동이 하나다.** Workspace가 없으면 "작업공간 등록" 버튼만 보이고, 등록하면 조정자 카드에 "첫 작업 맡기기 →"가 뜬다.
- **의뢰 창의 기본 입력은 넷뿐이다.** 요청문, 작업 방식, "파일 수정 허용", "계획을 보고 시작". 엔진·모델·우선순위·선행 조건은 접힌 "작업별 옵션" 안에 있다.
- **기본값이 안전하다.** 읽기 전용이 기본이고 수정은 의뢰마다 켠다.
- **좁은 화면에서 깨지지 않는다.** 폭 390px에서 가로 넘침이 없다(`scrollWidth == clientWidth`).
- **접근성 기초가 있다.** 건너뛰기 링크, 입력마다 `label`, 캐릭터 이동 일시정지 버튼.
- **데스크톱 앱에는 폴더 선택기가 있다**(`desktop/main.mjs:245`).

### 문제

**U-1. 화면 체계가 둘로 갈라져 있고 같은 일을 하는 길이 여섯 개다.** `확실`

| 주소 | 모습 | 하는 일 |
| --- | --- | --- |
| `/`, `/workspace` | 어두운 조선 서재 화풍, 로고 "房 AI Agent Office" | Workspace 선택, 조정자에게 의뢰, 요청함, 설정 |
| `/bots` | 같은 화풍이지만 머리글 구성과 글꼴이 다름 | 봇 회의실, 봇 대화, 왕명, 봇 파일 편집 |
| `/studio` | 밝은 녹색, 로고 "Agent Office" | "새 작업" 양식(다른 옵션 구성), Workspace 등록(중복), 스킬 관리, 엔진 진단, 요청함, 실행 기록 |
| `/office`, `/versions`, `/improvements` | `/studio` 와 같은 밝은 화풍 | 오피스 보기, 안정 버전 이력, 자체 개선안 |

제품 이름까지 두 가지로 보인다. 작업을 맡기는 길은 ①조정자 대화 ②봇 대화 ③왕명 ④`/studio` 의 새 작업 양식 ⑤GitHub Issue 라벨 ⑥CLI `agent-office run` 이고, 각각 쓸 수 있는 옵션이 다르다(예: "독립 하위 작업으로 나눠 실행"과 "역할별 스킬 선택"은 `/studio` 에만 있다). 게다가 Workspace를 하나라도 등록하면 `/` 가 봇 회의실을 열도록 바뀐다(`studio_server.py:298`). 처음 본 화면이 두 번째 방문 때는 다른 화면이 된다.

**U-2. 용어가 일관되지 않다.** `확실`
설정 창 하나에 같은 역할이 세 이름으로 나온다: "담당자/검토자"(엔진 선택), "개발 담당/검토 담당"(기본 표시 이름), "개발자/리뷰어"(역할 봇의 실행 자리). 그 밖에 작업공간·작업실·Workspace·프로젝트 작업실, 밤샘 목표·장시간 개발 목표·야간 목표, 왕명·어명이 섞인다. 내부 열거값이 그대로 보이는 곳도 있다("호스트 모델 목록 · unprobed · 조회 시각 미확인").

**U-3. 첫 실행에서 준비 상태를 알려 주지 않는다.** `확실`
첫 화면은 "폴더를 등록해 작업실을 열 수 있습니다" 한 줄이다. 이 제품이 무엇을 하는지, 어떤 CLI가 설치·로그인돼 있어야 하는지, 지금 이 PC에서 무엇이 준비됐는지는 나오지 않는다. 엔진 상태는 의뢰 창의 접힌 옵션 안 선택 목록("Codex · CLI 확인", "Cline CLI · 설치 필요")에서야 보인다. 웹 Studio에서는 폴더의 절대 경로를 손으로 입력한다.

**U-4. 결과를 반영하는 길이 없다.** `확실`
검증이 끝난 실행은 "사람 검토 대기" 상태가 된다. 그다음 사용자가 할 수 있는 일은 화면에서 diff와 테스트 출력을 읽는 것까지다. 변경을 원래 체크아웃에 적용하거나, 이름 있는 브랜치로 내보내거나, PR을 만드는 버튼이 없다. 장시간 목표의 "채택"은 `studio_goals.adopted_attempt` 를 갱신하는 기록이다(`overnight_goals.py:233-264`). PR 초안 게시는 `github_publish.py` 에 있지만 GitHub App 연결이 전제다. README도 "여러 worktree의 변경을 함께 반영할 때에는 사람이 검토하고 통합 결과를 검증합니다"라고만 적는다. 결과적으로 사용자는 터미널에서 `ao/task-<32자리>` 브랜치를 직접 병합해야 한다. worktree 정리도 "종료 후 7일이 지난 작업 트리"를 설정 창에서 수동으로 고르는 방식이다. 경쟁 제품에서 "diff 검토 → 커밋·푸시·PR"은 기본 기능이다.

**U-5. 알림이 없다.** `확실`
웹과 데스크톱 코드 어디에도 OS 알림, 트레이, 배지, 소리가 없다(`new Notification`, `Tray`, `setBadge` 검색 결과 0건). 여러 에이전트를 맡겨 두는 제품에서 "지금 내 응답이 필요한 곳"을 알리는 것은 핵심 기능이다. `docs/product-vision.md` 가 flowmux에서 채택하겠다고 적은 동선("알림을 누르면 해당 세션으로 돌아간다")의 앞 절반이 빠져 있다. 화면은 열려 있을 때만 주기적으로 갱신한다(유휴 시 20초, `docs/verification.md`).

**U-6. 워커가 지금 무엇을 하는지 보이지 않는다.** `보통`
실행마다 "마지막 공급자 활동" 한 줄과 시각을 보여 주고 최근 128건만 보존한다. 프롬프트, 터미널 원문, 도구 입력은 저장하지 않는다(`docs/engines.md`). 감사 기록으로는 절제된 선택이지만, 15분짜리 호출이 도는 동안 사용자가 볼 것이 거의 없다. 경쟁 제품은 터미널이나 도구 호출 단위 스트림을 그대로 보여 준다.

**U-7. Studio의 수정 실행은 pytest만 돈다.** `확실`
`studio_runner.py:634-635` 가 테스트 명령을 `[sys.executable, "-m", "pytest", "-q"]` 로 고정하고, 일반 실행의 테스트 단계는 종료 코드 0만 통과로 본다(`workflow.py:267-275`, 제한 300초). Node·Go·Rust 저장소에서는 pytest가 테스트를 찾지 못해 실패하고 재작업 한도를 소진한다. 장시간 목표의 검증 설정에는 `npm test`, `cargo test`, `go test ./...`, 호스트 등록 검사가 있지만(`project_checks.py:16-24`, `goal_checks.py:38-52`) 고정된 조합만 받는다. CLI `run` 에는 `--test-command` 가 있는데 Studio에는 없다.

**U-8. 한국어 전용이다.** `확실`
모든 페이지가 `<html lang="ko">` 이고 문자열이 코드에 박혀 있다. 메시지 카탈로그나 언어 전환이 없다. README는 한국어와 영어가 절마다 섞여 있다. 한국어권에 집중하는 것은 전략이 될 수 있지만 지금은 선택이 아니라 구조상 제약이다.

**U-9. 실행 한도가 작고 사용자에게 드러나지 않는다.** `확실`
요청문 8,192바이트, 워커 호출 900초, 테스트 300초, Claude Code는 `--max-turns 16` 고정(`adapters.py:57`), ACP 응답은 12,000자에서 잘림(`adapters.py:98`). 큰 작업에서는 조용히 잘리거나 시간 초과로 "복구 필요"가 된다. Workspace 설정에서 바꿀 수 없다.

**U-10. 캐릭터 프로필(육각형 능력치)은 자료가 쌓이기 전까지 빈 상자다.** `보통`
조정자 대화의 "캐릭터 프로필과 작업 근거"는 분석·구현·검증·리뷰·프로젝트 이해·협업 여섯 축을 보여 주는데 새 Workspace에서는 전부 "자료 부족 · 표본 0건"이다. 첫 사용자에게는 뜻을 알 수 없는 영역이다.

## 4. 봇 확장성 진단

### 봇이 실제로 하는 일

봇을 만들 때 입력하는 것은 이름, 자유 역할, 업무 지침, 캐릭터 그림이다. 실행 시점에 봇은 아래처럼 변환된다(`goal_workers.py:226-250`).

- 조정자 봇과 해당 역할 봇의 `instructions`(= `SOUL.md`)를 JSON에 담는다.
- 해당 역할 봇의 파일 중 확장자가 `.md` 또는 `.txt` 이고 최상위 폴더가 `mcp`, `hooks` 가 아닌 것을 전부 같은 JSON에 넣는다.
- 개발자 자리에는 같은 봇의 최근 대화를 덧붙인다(최대 네 쌍, 발화당 1 KiB — `bot_runtime.py:54`, `docs/bot-client.md`).
- 이 JSON을 프롬프트 첫 줄 뒤에 끼운다. 그 밖의 것(외형, 확장 값, 빈 폴더, `mcp/`, `hooks/`)은 보관만 한다.

즉 봇 = 프롬프트 앞머리다. 엔진, 모델, 권한, 도구는 봇이 아니라 Workspace가 정한다.

### 구성요소별 실제 동작

| `MEMORY.md` | 예 (사람이 편집) | 저장돼 있으면 `.md` 자산으로 포함 | 봇이 스스로 갱신하지 않음 | `local_bots.py:179`, 쓰기 경로 없음 |

### 문제

**B-1. 봇에게 능력을 줄 방법이 없다.** `확실`
MCP 서버 연결, 스크립트가 있는 스킬, 외부 서비스 접근 어느 것도 봇 단위로 붙일 수 없다. 봇을 설치해 얻는 것은 글이다.

**B-2. 실행 자리는 셋으로 고정이고, 사용자 정의 역할은 표시용이다.** `확실`
파이프라인은 조정자·개발자·리뷰어 세 자리만 호출한다. 회의실에서 "UX 리서처" 봇에게 메시지를 보내면 그 봇이 개발자 자리에 앉은 일반 실행이 만들어지고, Workspace의 개발 엔진으로 돈다(`docs/bot-room-live-verification.md`: "왕명은 해당 Workspace에 선택된 개발 엔진으로 각 봇의 실행을 생성한다"). 최초 구상(`docs/CODEX_HANDOFF_2026-11-06.md`)의 Planner, Architect, Tester, Domain Expert 같은 역할 구분은 구현돼 있지 않다.

**B-3. 왕명의 분담은 정규식이고, 봇끼리는 협업하지 않는다.** `확실`
분담안은 브라우저에서 만든다. `이름: 할 일` 형식의 줄이 있으면 그것을 쓰고, 없으면 역할 이름의 키워드(디자인, 기록 등)에 맞춘 고정 문구나 "`{역할}` 관점에서 필요한 작업을 진행하고 결과를 보고"를 채운다(`web/bot-client-orders.js:65-72`). 서버는 봇마다 독립 실행을 만들 뿐이다(`bot_runtime.py:168-229`). 봇 사이의 결과 전달, 순서 의존, 종합 보고가 없다. 화면의 "왕이 신하들에게 일을 나눠 준다"는 연출과 실제 동작(같은 문장에 꼬리표를 붙여 N번 실행) 사이의 간극이 크다.

**B-4. 기억이 쌓이지 않는다.** `확실`
`MEMORY.md` 는 사람이 편집기에서 써야 한다. 작업이 끝난 뒤 봇이 배운 것을 남기는 경로가 없다. 연속성은 최근 대화 네 쌍이 전부다.

**B-5. 트리거가 없다.** `확실`
일정, 웹훅, 메신저, 멘션으로 봇을 깨우는 기능이 없다. GitHub Issue 연동은 봇이 아니라 Workspace의 목표로 들어간다. 봇은 사람이 화면에서 말을 걸 때만 일한다.

**B-6. 봇 수명주기 관리가 없다.** `보통` (확인 범위: `local_bots.py`, `web_bot_api.py`, `bot_cli.py`, `web/bot-client*.js`)
삭제, 이름 변경, 복제, 보관, 버전 이력, 사용 통계를 찾지 못했다. 봇 관련 테이블에서 지우는 것은 역할 배정뿐이다(`local_bots.py:280`). 회의실 화면에도 봇을 지우는 버튼이 없다. 시험 삼아 만든 봇이 계속 남는다.

**B-7. 크기 한도가 실제 스킬 묶음을 담지 못한다.** `확실`
파일당 8 KiB, `SOUL.md` 외 합계 24 KiB, 최대 32개(`docs/bot-spec-v1.md`; 로컬 저장 검증은 자산 15개 — `local_bots.py:64`). 그리고 전부 프롬프트에 한 번에 들어간다. 참고 자료가 조금만 커져도 한도에 걸리고, 걸리지 않아도 매 호출의 토큰을 쓴다.

**B-8. 공유 경로가 좁다.** `확실`
공개 HTTPS Git 저장소의 443 포트만 받는다. 자격증명 도우미를 끄기 때문에 비공개 저장소나 사내 Git은 쓸 수 없다(`git_bot_source.py:53-54, 118, 252`). 카탈로그 주소는 이 저장소의 `main` 으로 고정이고(`shared_bot_catalog.py:14`) 항목은 예제 하나다. 등재는 이 저장소에 PR을 보내는 방식이며 검수·서명 절차가 없다.

**B-9. 기존 자산을 가져올 다리가 없다.** `보통`
패키지 매니페스트로 Agent Plugins `plugin.json` 을 택한 것은 맞는 방향이다. 그러나 개발자들이 이미 가진 것 — Claude Code의 서브에이전트(`.claude/agents/*.md`)와 스킬 폴더, `AGENTS.md`, Orca 봇 — 을 읽어 들이는 기능이 없다. 새 형식을 쓰려면 처음부터 다시 써야 한다.

### 이 영역의 강점

스키마(JSON Schema Draft 2020-12)와 적합성 테스트, 경로·유니코드·Windows 장치명 검증, 커밋 SHA와 정의 해시로 고정한 설치, 충돌을 표시하고 멈추는 업데이트, 오프라인 한 단계 롤백, 공유본에서 `MEMORY.md` 제외, DNS·예약 주소 차단. 실행마다 당시 봇 정의의 사본과 해시를 남기는 것도 감사 관점에서 좋다. **문제는 품질이 아니라 범위다.** 단단하게 만든 것이 "텍스트 묶음의 교환"까지다.

## 5. 엔진 확장성과 완성도 진단

### 엔진

**E-1. 엔진이 분기문으로 고정돼 있다.** `확실`
`CLIAdapter` 하나가 엔진 이름으로 분기해 명령줄을 만든다(`adapters.py:40-64`). 엔진 목록은 `engines.py:8` 의 사전이다. 엔진 이름을 비교하는 분기가 Python 15개 파일에 약 66곳(`adapters.py` 10, `acp.py` 10, `batch_dialogue.py` 9, `work_profiles.py` 6, `engine_updates.py` 5, `engine_status.py` 5 …), 웹 JS·HTML 6~7개 파일에도 이름이 박혀 있다. 공통 인터페이스, 등록부, 플러그인 진입점이 없다. 여섯 번째 엔진을 넣으려면 이 지점들을 모두 찾아 고쳐야 한다. Orca는 "터미널에서 프로세스를 띄우는 것"으로 아무 CLI나 받고, 십수 종을 사전 구성해 제공한다.

**E-2. 공급자 CLI의 변화에 약하다.** `확실`
Cline은 3.0.74 이상에서만, 그것도 호스트별 실검증 기록이 있어야 수정 권한을 연다(`engines.py:11`, `adapters.py:95-96`). Claude Code는 도움말 문구로 지원 여부를 판단하다가 `--max-turns` 가 도움말에서 빠지자 실행이 막혔고 PR #55로 고쳤다. 보수적으로 막는 방향은 옳지만, 공급자가 주 단위로 CLI를 바꾸는 상황에서 유지 비용이 계속 든다.

**E-3. 기본 엔진 선택 자체가 위험이다.** `재확인 필요` → 6장 M-1, M-2 참조.

**Q-6. 버전과 문서가 어긋나 있다.** `확실`
- 버전: 0.1.0 / 0.10.0 / 0.7.0 (2장).

**Q-7. 개발 환경이 스스로 어긋나도 알려 주지 않는다.** `확실`

## 7. 포지셔닝 — 소유자가 정해야 할 것

지금의 제품은 세 가지를 동시에 하려 한다: ①범용 멀티 에이전트 작업실 ②봇 플랫폼 ③자기 자신을 개발하는 시스템. 1인 프로젝트가 셋 다 Orca 수준으로 만들 수는 없다. 하나를 중심에 놓아야 한다.

| 안 | 대상 | 핵심 약속 | 필요한 것 | 위험 |
| --- | --- | --- | --- | --- |
| **A. 검증 근거가 붙은 무인 실행** | 밤사이·부재중에 일을 맡기고 싶은 1인 개발자와 소규모 팀 | "아침에 돌아오면 테스트와 독립 리뷰를 통과한 PR과 그 근거가 있다" | P0 전부, 장시간 목표의 다중 스택 검증, PR 게시, 알림 | 범위를 줄이는 결단. 봇·회의실 연출은 보조로 내려감 |
| B. 한국어권 개발자의 에이전트 작업실 | 한국어 사용자 | 한국어 UI·문서·커뮤니티, 개성 있는 화면 | 커뮤니티 운영, 한국어 콘텐츠, 템플릿 봇 | 시장이 작다. 기능 열위는 그대로 |
| C. 큰 도구의 보완재 | Orca·Claude Code·CI 사용자 | 검증 파이프라인과 감사 기록을 CLI·스킬·플러그인으로 제공 | `agent-office verify` 류의 독립 명령, Agent Plugins·스킬 패키징 | 데스크톱 앱의 존재 이유가 약해짐 |

**권고: A를 제품의 중심으로, C를 배포 경로로, B를 초기 커뮤니티로.**
이유는 6장의 비교표다. 이 제품이 앞서는 것은 "권한 기본값"과 "내장 검증" 두 줄이고, 둘 다 A의 약속을 직접 받친다. 시장의 큰 제품들은 속도와 병렬성을 팔고 있고 권한 확인 생략이 기본이다. "느리더라도 근거가 남는다"는 자리는 비어 있다. 봇 회의실과 캐릭터는 버리지 말고 A의 입구(무슨 일이 진행 중인지 한눈에 보는 화면)로 쓴다.

이 권고를 받아들이지 않고 봇 플랫폼(②)을 중심에 둔다면 8장의 P1-1~P1-6이 P0가 되고, 그 경우에도 P0-1(약관), P0-2(반영), P0-6(배포 신뢰)은 먼저 해야 한다.

> **개정 1의 결정.** 소유자는 Orca의 봇 방식을 적극 도입하고(②를 중심에), 지금은 개발과 개인 사용을 우선하기로 했다. 따라서 위 권고 A는 버리는 것이 아니라 봇 안으로 들어간다: 봇이 맡긴 수정은 지금의 검증 파이프라인을 거치는 워커가 수행한다(14장 "지킬 것"). 배포 신뢰(P0-6)와 홍보 성격의 작업은 보류한다.

### P1 — 봇과 엔진의 확장성

**P1-1. 봇 실행 프로필** (M) — B-1, B-2
봇 정의에 확장 `io.github.tworimpa.agentoffice.runtime` 을 추가해 선호 엔진·모델·추론 강도·기본 권한(읽기 전용/수정)을 담는다. 실행 시 Workspace 정책이 허용하는 범위에서 적용한다. 공개 명세(1.0)는 그대로 두고 확장으로 넣으므로 호환이 깨지지 않는다.
완료 기준: 봇 A는 Claude Code, 봇 B는 Codex로 같은 Workspace에서 실행된다. 미설치 엔진을 요구하는 봇은 설치 미리보기에서 경고한다.

**P1-2. 봇 파일을 파일로 전달** (M) — B-7
지금처럼 JSON에 통째로 넣지 말고, 실행 worktree 옆의 읽기 전용 폴더에 봇 파일을 풀어 놓고 프롬프트에는 `SOUL.md` 와 파일 목록만 넣는다. 엔진이 필요할 때 읽는다. 그러면 24 KiB 한도를 올릴 수 있고(다음 명세 버전), 매 호출의 토큰이 준다.
완료 기준: 200 KiB짜리 참고 자료를 가진 봇이 설치·실행된다. 프롬프트 크기가 자료 크기와 무관하다.

**P1-3. 봇 도구(MCP)** (L) — B-1
`mcp/servers.json` 을 "보관만"에서 "설치 시 사용자가 서버별로 승인하면 실행에 연결"로 바꾼다. MCP 설정을 받는 엔진(Claude Code, Codex 등)에만 적용하고, 승인 기록과 서버 명령을 실행 저널에 남긴다. 승인 없이는 지금과 같이 아무것도 실행하지 않는다.
완료 기준: 승인한 MCP 서버의 도구를 봇이 호출하고, 승인하지 않은 서버는 시작되지 않는다. 설치 미리보기가 실행될 명령을 그대로 보여 준다.
주의: 보안 정책 변경에 해당한다. 소유자 승인 필요(10장 ⑤).

**P1-4. 기억 제안** (M) — B-4
실행이 끝나면 봇에게 "다음에 기억할 것"을 `MEMORY.md` diff로 제안하게 하고, 사용자가 승인하면 저장한다. Workspace에서 "자동 승인"을 켤 수 있다. 공유 패키지에서는 지금처럼 제외한다.
완료 기준: 두 번째 의뢰의 프롬프트에 첫 의뢰에서 승인한 기억이 들어 있다.

**P1-5. 트리거** (L) — B-5
①일정: 봇에 cron 식과 고정 의뢰문을 붙인다. Studio가 떠 있을 때 실행하고, 놓친 일정은 건너뛴다. ②GitHub: 기존 이슈 동기화(`github_sync.py`)에 "이 라벨은 이 봇에게"를 추가한다. 메신저·웹훅은 그 뒤.
완료 기준: "매일 09:00 어제 병합된 변경 요약"이 읽기 전용으로 돌고 결과가 봇 대화에 쌓인다.

**P1-6. 왕명을 실제 조정으로** (M) — B-3
분담안을 정규식이 아니라 이미 있는 조정자 계획 기능(`meeting_runtime.py`)으로 만든다. 봇별 담당과 선행 관계를 제안받아 사용자가 고치고 승인한다. 끝나면 조정자가 결과를 한 문서로 묶는다.
완료 기준: 두 봇의 결과가 하나의 종합 보고로 왕명 기록에 남는다. 선행 봇의 결과가 후속 봇의 입력에 들어간다.

**P1-7. 봇 수명주기와 가져오기** (M) — B-6, B-9
삭제(실행 기록의 고정 사본은 보존), 이름 변경, 복제, 정의 변경 이력. 가져오기: Claude Code 서브에이전트(`.claude/agents/*.md`), Agent Skills 폴더, `AGENTS.md` → Bot Definition 변환. 시작 템플릿 10종 이상(코드 리뷰어, 테스트 작성자, 릴리스 노트 작성자, 의존성 점검 등)을 카탈로그에 올린다.
완료 기준: 기존 `.claude/agents/reviewer.md` 를 한 번에 봇으로 만든다. 카탈로그 항목이 10개 이상이다.

**P1-8. 비공개 공유** (M) — B-8
카탈로그 주소를 설정으로 빼고 여러 개를 받는다. 비공개 Git은 호스트의 Git 자격증명을 쓰도록 선택하게 한다(기본은 지금처럼 끔).
완료 기준: 사내 Git 저장소의 봇 패키지를 설치·업데이트한다.

**P1-9. 엔진 등록부** (L) — E-1, E-2
엔진을 선언형 프로필(실행 파일, 읽기·수정 모드의 인자, 출력 파서, 지원 기능, 인증 확인 명령)로 정의하고 `CLIAdapter` 의 분기를 프로필 조회로 바꾼다. 웹은 `/api/engines` 가 주는 목록을 그린다. ACP를 말하는 CLI는 공통 ACP 프로필로 추가할 수 있게 한다. OpenCode, GitHub Copilot CLI, Cursor CLI를 이 방식으로 넣어 본다.
완료 기준: 새 엔진 추가가 프로필 파일 하나와 계약 테스트 하나로 끝난다. 엔진 이름 비교 분기가 `adapters.py`·`acp.py` 밖에서 사라진다.

**P1-10. 진행 상황 보기** (M) — U-6
실행 상세에 도구 호출 단위의 활동 흐름을 선택적으로 보여 준다(기본 꺼짐, 비밀값 마스킹 적용, 실행 종료 후 보존 기간 설정).
완료 기준: 수정 실행 중 "어떤 파일을 읽고 고쳤는지"가 실시간으로 보인다.

**P1-11. 다국어 기반** (M) — U-8
UI 문자열을 메시지 카탈로그로 빼고 한국어·영어를 제공한다. P0-5의 용어집을 카탈로그의 출발점으로 쓴다.

## 12. 설계 — `gh` 로 결과 반영하기 (개정 1)

**전제가 되는 사실.**
- 워커는 `gh` 와 Git 네트워크 전송을 쓸 수 없다. 워커 환경은 `gh` 자리에 실패하는 가짜 실행 파일을 두고, 자격증명 변수를 지우고, `GIT_ALLOW_PROTOCOL=":"` 와 `remote.origin.pushurl=no-push://blocked` 를 건다(`worker_environment.py:19-34`). 이 차단은 그대로 둔다.
- 따라서 반영은 **Studio(호스트) 프로세스가, 사람이 버튼을 눌렀을 때** 수행한다. 워커 프롬프트의 "커밋·푸시·병합 금지"는 바뀌지 않는다.
- GitHub App 연결을 쓰는 기존 게시 경로(`github_publish.py`)는 이슈 연동 같은 무인 흐름용으로 남긴다. `gh` 경로는 개인 사용의 기본이 된다.

**흐름.**

| 순서 | 호스트가 하는 일 | 실패 시 |
| --- | --- | --- |
| 0. 준비 확인 (화면을 열 때, 모델 호출 없음) | `gh --version`, `gh auth status` 의 종료 코드, `origin` 이 GitHub 저장소인지, `gh repo view --json defaultBranchRef,viewerPermission` | 버튼 대신 "gh 로그인 필요" 또는 "GitHub 원격 없음 — 로컬 브랜치로 내보내기만 가능" 표시 |
| 1. 확인 창 | 대상 저장소, 기준 브랜치, 새 브랜치 이름(기본 `office/<요청 요약>-<실행 ID 앞 8자>`), 포함될 파일 목록, 커밋 메시지(수정 가능)를 보여 준다 | — |
| 2. 커밋 | 실행 worktree에서 변경을 스테이징하고 사용자의 Git 신원으로 한 커밋을 만든다. 메시지 끝에 실행 ID를 적는다. 기준 커밋이 실행 접수 때 고정한 값과 같은지 확인한다 | 아무것도 바꾸지 않고 사유 표시 |
| 3. 푸시 | `git push origin <브랜치>` 를 호스트 환경(사용자 자격증명)으로 실행 | 커밋은 남기고 "푸시 실패" 기록. 재시도 가능 |
| 4. PR 초안 | `gh pr create --draft --base <기준> --head <브랜치> --title … --body-file …`. 본문은 원 요청, 실행한 검증 명령과 결과 요약, 리뷰 판정, 미검증 항목, 실행 ID | 브랜치는 남기고 재시도 가능 |
| 5. 기록 | 저널에 커밋 SHA, 브랜치, PR 주소, 시각을 남긴다. 같은 실행에서 다시 누르면 `gh pr list --head <브랜치>` 로 기존 PR을 찾아 돌려준다 | — |
| 6. 추적 | 실행 상세에서 `gh pr view --json state,statusCheckRollup` 으로 PR 상태와 CI 결과를 보여 준다. 병합되거나 닫히면 worktree와 `ao/task-*` 브랜치 정리를 제안한다 | — |

**`gh` 가 없거나 GitHub 저장소가 아닐 때.** 2단계까지만 하고 "로컬 브랜치로 내보내기"로 끝낸다. 사용자는 그 브랜치를 직접 병합한다.

**하지 않는 것.** 제품 안에서 병합하지 않는다. 병합은 PR에서 사람이 한다. 원래 체크아웃에 패치를 직접 적용하는 기능(초판 P0-2의 ②)은 뒤로 미룬다. PR 경로가 있으면 급하지 않다.

**손댈 곳.** 새 모듈(예: `gh_adopt.py`)에 준비 확인·커밋·푸시·PR 생성을 두고, `studio_server.py` 에 라우트 둘(준비 확인 GET, 반영 POST), `web/office-content.js` 에 버튼과 확인 창, `worktree_storage.py` 에 "반영된 실행" 정리 조건. `gh` 실행 파일은 `engines.resolve_executable` 로 찾는다(저장소 안의 동명 파일을 집지 않도록).

**테스트.** 이 저장소가 엔진에 쓰는 방식대로 가짜 `gh` 실행 파일 fixture와 로컬 bare 저장소를 원격으로 써서 Windows·Linux CI에서 검증한다. 확인할 것: 준비 미달 시 거절, 같은 요청 재전송 시 PR 하나만 생김, 푸시 실패 후 재시도, 워커 환경에서는 여전히 `gh` 가 막혀 있음.

**정해야 할 것.**
1. 병렬 하위 작업(부모 실행 하나에 자식 여럿)은 자식마다 PR인가, 통합 PR 하나인가. 권고: 처음에는 자식마다.
2. 장시간 목표의 "채택"과 PR 만들기를 한 동작으로 묶을 것인가. 권고: 채택한 후보에만 PR 버튼을 보인다.
3. `docs/decisions.md` 에 "호스트는 운영자의 명시적 조작으로 브랜치를 푸시하고 PR 초안을 만들 수 있다"는 결정 기록을 추가한다. 지금의 ADR-003과 README 문구는 워커와 호스트를 구분하지 않고 "push 금지"로 읽힐 수 있다.

## 13. 검토 — pytest 고정의 대체 방안 (개정 1)

### 문제를 둘로 나눠야 한다

1. **무슨 명령으로 검증하나.** Studio의 일반 수정 실행은 `sys.executable -m pytest -q` 고정이다(`studio_runner.py:634-635`). 여기서 `sys.executable` 은 **Studio 자신의 Python**이다. 그래서 Python 프로젝트라도 그 프로젝트의 가상환경이 아니라 Studio의 환경에서 테스트가 돈다. 프로젝트 의존성이 Studio 쪽에 없으면 import 단계에서 실패한다. pytest 고정은 "Python만 된다"가 아니라 "Studio와 의존성이 겹치는 Python 프로젝트만 된다"에 가깝다.
2. **새 worktree에 의존성이 어디서 오나.** 실행마다 만드는 worktree에는 Git이 추적하지 않는 것(`node_modules`, `.venv`, `.env`)이 없다. 장시간 목표의 npm·cargo·go 조합은 `--offline`, `--ignore-scripts`, `GOPROXY=off` 로 돈다(`project_checks.py:38-58`, `goal_checks.py:160-165`). 캐시가 있는 cargo·go는 되지만 Node 프로젝트는 `node_modules` 가 없어 실패한다. 명령만 일반화해서는 풀리지 않는다.

### 이미 저장소에 있는 부품

| 부품 | 하는 일 | 위치 |
| --- | --- | --- |
| CLI `--test-command` | 임의 명령을 테스트 단계에 넘김. Studio에는 노출 안 됨 | `cli.py:71` |
| 고정 조합 | pytest, `npm test`/`npm run test:*`, `cargo test`, `go test ./...` 를 오프라인·비특권 세션에서 실행하고 영수증을 남김 | `project_checks.py`, `goal_checks.py` |
| 호스트 등록 검사 | 운영자가 프로젝트 밖 파일에 등록한 임의 명령을 SHA-256으로 고정해 실행. JUnit 또는 종료 코드 | `goal_host_checks.py` |

| A. Workspace 검증 명령 | Workspace 설정에 인자 배열로 명령을 저장. 예: `uv run pytest -q`, `pnpm test`, `dotnet test`, `make check` | 어떤 스택이든 됨. 구현이 작음(이미 `test_argv` 로 흐름) | 명령을 사람이 정해야 함. 오프라인 보장 없음 | **채택 권고(핵심)** |
| B. 문서에서 기본값 제안 | A의 입력란을 `away_evidence` 의 추출 결과와 매니페스트 감지로 미리 채움 | 대부분 입력 없이 맞음. 기존 코드 재사용 | 추출 실패 시 빈칸 | **채택 권고(A의 보조)** |

### 권고

**A + B + C를 한 묶음으로 구현하고, D는 무인 실행(장시간 목표)의 엄격한 길로 남긴다. E는 12장이 끝난 뒤 얹는다.**

구체적으로:

1. **Workspace 설정에 "검증" 절을 만든다.** 항목: 검증 명령(인자 배열, 여러 줄 가능), 제한 시간, 결과 형식(종료 코드 / JUnit 파일 경로). 처음 열 때 B의 제안을 채워 보여 주고 사용자가 확인한다. 명령은 Workspace를 등록한 사람이 자기 PC에서 정하는 것이므로 CLI의 `--test-command` 와 같은 신뢰 수준이다.
2. **명령이 없을 때의 기본 동작을 바꾼다.** 지금은 pytest를 돌려 실패한다. 바꾼 뒤에는 "자동 검증 없음"으로 기록하고 리뷰 단계로 넘어가며, 결과 화면에 미검증이라고 표시한다. 조용히 통과로 보이게 하지 않는다.
3. **작업 트리 준비를 추가한다.** 실행 worktree를 만든 직후, 테스트와 워커 호출 전에: 공유 목록의 디렉터리를 원본 체크아웃에서 링크하고(Linux 심볼릭 링크, Windows 디렉터리 정션), 복사 목록의 파일을 복사하고, 준비 명령이 있으면 실행한다. 준비 명령의 출력과 종료 코드는 실행 기록에 남긴다.
4. **Python 프로젝트의 인터프리터를 고른다.** 프로젝트에 `.venv` 가 있거나 `uv.lock` 이 있으면 B가 `uv run pytest -q` 또는 그 가상환경의 Python을 제안한다. Studio 자신의 Python으로 남의 프로젝트를 테스트하는 지금의 기본값은 없앤다(이 저장소 자신을 개발할 때만 우연히 맞았던 값이다).
5. **장시간 목표는 지금의 고정 조합과 호스트 등록 검사를 그대로 쓴다.** 사람이 없는 동안 도는 검증은 더 엄격해야 한다. 다만 C의 준비 단계는 같이 적용해 Node 프로젝트가 돌게 한다. 이때 공유 디렉터리는 `project_checks.dependency_inputs` 가 이미 요구하는 조건(프로젝트 안의 실제 디렉터리)과 충돌하므로, 무인 경로에서는 링크 대신 복사를 쓴다.

**손댈 곳.** `studio_runner.py:634-640`(명령 선택), `workflow.py` 의 `test` 노드(명령 없음 처리, 제한 시간), `workspace.py` 또는 `worktree_storage.py`(준비 단계), `studio_catalog.py`(설정 저장과 검증), `away_evidence.py` 의 추출 함수를 공용으로 꺼내기, `web/workspace-profile.js`.

**완료 기준.**
- Node·Go·Rust fixture 저장소에서 수정 실행이 검증 단계를 통과한다.
- `.venv` 를 가진 Python fixture가 Studio에 없는 의존성을 import하는 테스트를 통과한다.
- 검증 명령이 없는 저장소는 "미검증"으로 사람 검토에 도달한다.
- 공유한 `node_modules` 가 실행 종료 후에도 원본과 같은 상태다(워커가 건드렸으면 기록에 남는다).

**남는 위험.** 링크로 공유한 디렉터리는 worktree 격리의 구멍이다. 워커가 `node_modules` 안을 고치면 원본 체크아웃에 영향이 간다. 완화: 공유 디렉터리의 실행 전후 지문을 비교해 달라졌으면 실행을 "검토 필요"로 표시한다. 완전한 해법은 F(컨테이너)다.

### 지금 구조와의 차이

**가장 큰 차이는 "봇이 어디서 사는가"다.** Orca의 봇은 자기 폴더에서 오래 사는 세션이고, 코드 작업은 워커에게 맡긴다. 지금 Agent Office의 봇은 SQLite 안의 JSON이고, 실행 때마다 개발자 자리의 프롬프트 앞머리로 풀린다(4장). 기억·도구·트리거·위임이 없는 것은 모두 여기서 나온다. 그래서 도입의 첫 걸음은 기능 추가가 아니라 **봇을 홈 폴더와 세션으로 옮기는 것**이다.

| Orca 개념 | Agent Office의 지금 | 도입안 |
| --- | --- | --- |
| 봇 홈 폴더 | 저널 안의 JSON | 호스트 데이터 폴더에 봇별 홈을 만든다. 저널은 색인과 해시, 변경 이력을 가진다 |
| 봇 세션 | 개발자 자리의 일회 실행 | 봇 홈을 작업 디렉터리로 한 세션. 엔진의 세션 재개를 써서 대화를 잇는다(`batch_dialogue.py` 에 재개 인자가 이미 있다) |
| 워커 | 실행(run) — worktree, 개발→검증→리뷰 | **그대로 워커로 쓴다.** 봇이 맡기면 실행이 생긴다 |
| 워커의 PR | 없음 | 12장의 `gh` 반영 |
| Needs you | 요청함(실행 단위) | 봇 Home에 그 봇의 질문·승인·검토 대기를 모아 보여 준다 |
| 일정·이벤트 | 없음 | 호스트 일정과 `gh` 폴링 |
| `orca` CLI | 없음 | `agent-office bot …` 하위 명령 또는 요청 파일(아래) |
| 그룹 방 | 왕명(정규식 분담, 독립 실행 N개) | 회의실에서 `@봇이름` 으로 부르고 서로 부를 수 있게 |
| Bot Definition 1.0 | 저장과 교환 형식 | **교환 형식으로만** 남긴다. 가져오면 홈 폴더로 풀고, 내보낼 때 홈에서 다시 만든다 |
| 실행 자리 3개 | 조정자·개발자·리뷰어 봇 | 워커의 역할 지침으로 남긴다. "봇"과 "워커 지침"을 화면에서 구분한다 |

### 지킬 것 — 그대로 베끼지 않는 부분

Orca를 따르되 이 제품이 앞서는 두 가지(6장)는 유지한다.

1. **봇은 코드를 직접 고치지 않고, 워커는 검증 파이프라인을 거친다.** 봇 세션은 저장소를 읽기만 하고 자기 홈에만 쓴다. 수정은 워커(실행)에게 맡기며, 그 실행은 지금처럼 검증·독립 리뷰·사람 검토를 거친다. Orca의 워커는 권한 확인 생략이 기본이지만 여기서는 아니다.
2. **봇이 밖으로 내보내는 동작은 호스트가 대신 수행하고 기록한다.** Orca는 봇이 소유자의 `gh` 를 직접 쓴다. 여기서는 워커 환경에서 `gh` 가 막혀 있다(`worker_environment.py`). 봇 세션에 `gh` 를 통째로 열기보다, 봇이 요청하고 호스트가 정책에 따라 실행하는 길을 기본으로 한다(아래 "봇이 호스트에 부탁하는 방법").

### 봇이 호스트에 부탁하는 방법

봇이 워커를 만들고, 질문을 남기고, 일정을 잡고, GitHub에 댓글을 달려면 호스트에 말을 걸 통로가 필요하다. 두 가지 방식이 있다.

| 방식 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| CLI | 봇이 셸에서 `agent-office bot delegate …` 를 부른다. CLI가 로컬 Studio API를 호출 | Orca와 같은 모양. 즉시 결과를 받음 | 엔진 샌드박스가 네트워크를 막으면 안 됨(Codex `workspace-write` 는 기본적으로 네트워크 차단 — `codex_inbox.py:342`). 엔진마다 셸 권한이 다름 |
| 요청 파일 | 봇이 홈의 `requests/<id>.json` 에 요청을 쓴다. 호스트가 턴이 끝날 때(또는 감시하다가) 읽어 검증하고 실행한 뒤 `results/<id>.json` 에 답을 쓴다 | 다섯 엔진 모두에서 됨(파일 쓰기만 필요). 네트워크 불필요. 요청이 그대로 감사 기록 | 한 턴 안에서 결과를 못 받음. 다음 턴에 이어 가야 함 |

**권고: 요청 파일을 기본으로 하고, 이 방식이 실제 엔진에서 잘 도는지 B3 착수 전에 짧게 시험한다.** 요청 종류는 처음에 다섯 개면 된다: `delegate`(워커에게 맡기기), `ask`(사람에게 묻기), `schedule`(일정 제안), `github`(읽기·댓글·라벨 — 호스트가 `gh` 로 실행), `reply`(트리거된 곳에 답하기). 사람 확인이 필요한 종류(수정 허용 위임, 일정 등록, GitHub 쓰기)는 봇별 설정으로 "매번 확인 / 자동 허용"을 고른다. 기본은 매번 확인.

### 단계

**B1. 봇 홈과 이어지는 대화** (L)
- 호스트 데이터 폴더 아래 `bots/<workspace>/<bot-id>/` 를 만든다. 내용: `SOUL.md`, `MEMORY.md`, `memory/`, 사용자가 넣은 파일들, 호스트가 생성하는 `AGENTS.md`·`CLAUDE.md`(프리앰블: 너는 누구인가, 홈의 파일 설명, 요청 파일 쓰는 법, 저장소는 읽기 전용이라는 것), `bot.json`.
- 봇 대화는 홈을 작업 디렉터리로 한 세션으로 돈다. 저장소는 원본이 아니라 그 턴을 위해 만든 읽기용 작업 트리로 준다. 엔진 샌드박스가 저장소 쓰기를 막아 주지 않기 때문이다(개정 4의 시험 결과). 같은 대화의 다음 메시지는 세션 재개로 잇는다. "새 대화"를 누르면 새 세션.
- 봇별 엔진·모델·추론 강도를 `bot.json` 에 둔다(초판 P1-1 흡수).
- 기존 봇은 처음 열 때 홈으로 옮긴다. 과거 실행에 고정된 정의와 해시는 그대로 읽힌다.
- 회의실 화면: 봇을 누르면 대화, 오른쪽 탐색기는 홈 폴더를 보여 준다(지금 UI 구조를 거의 그대로 쓸 수 있다).
- 완료 기준: 같은 대화에서 두 번째 메시지가 첫 메시지의 내용을 안다. 엔진을 바꾸면 새 대화가 열리고 옛 대화는 기록에 남는다. Windows와 WSL에서 실제 엔진으로 한 번씩 확인.

**B2. 스스로 쓰는 기억** (M)
- 봇은 자기 홈에 쓸 수 있으므로 `MEMORY.md` 와 `memory/` 를 직접 고친다. 호스트는 턴마다 홈의 변경을 저널에 스냅샷으로 남기고, 화면에 "이번에 기억한 것"을 diff로 보여 주며 되돌리기를 제공한다.
- `SOUL.md` 는 사용자가 요청할 때만 바꾸도록 프리앰블에 적고, 바뀌면 화면에 눈에 띄게 표시한다.
- 기억 정리(하루 한 번, 줄 수 상한)는 B5의 일정 기능 위에 얹는다.
- 공유 패키지에서 `MEMORY.md` 와 `memory/` 를 빼는 규칙은 유지한다.
- 완료 기준: 새 대화가 이전 대화에서 저장한 사실을 쓴다. 기억 변경을 한 번에 되돌릴 수 있다.

**B3. 봇이 워커에게 맡기기** (L)
- `delegate` 요청: 과제 문장, 대상 폴더, 수정 허용 여부. 호스트가 일반 실행을 만들고(지금의 `WorkspaceRooms.assign`), 실행에 "어느 봇이 맡겼는지"를 기록한다. 실행이 끝나면 결과 요약과 실행 링크를 봇의 다음 턴 입력으로 넣는다.
- 봇 아래에 그 봇이 만든 실행 목록을 보여 준다(Orca의 "봇 아래 워커").
- 실행이 사람 검토를 통과하면 12장의 PR 초안으로 이어지고, PR 주소가 봇 대화에 남는다.
- 지금의 "봇에게 메시지 = 개발자 자리 실행"은 없앤다. 봇에게 말하면 봇이 답하고, 필요하면 맡긴다.
- 완료 기준: "이 버그 고쳐 줘"라고 봇에게 말하면 봇이 워커에게 맡기고, 검증된 실행 결과와 PR 초안 주소가 같은 대화에 돌아온다.

**B4. 봇 Home — "내가 답할 것"** (M)
- 봇마다 Home 패널: ①내가 답할 것(질문, 승인, 검토 대기) ②진행 중 ③기다리는 중(사유: CI, 리뷰, 한도) ④예정 ⑤끝난 것 ⑥자동화.
- 지금의 요청함·조정자 브리핑·작업 기록을 봇 기준으로 다시 묶는 일이다. 이때 3장의 U-1(갈라진 화면)과 U-2(용어)를 함께 정리한다. 회의실이 제품의 첫 화면이 되고, `/studio` 는 운영자용으로 남는다.
- 알림(P0-7)은 "내가 답할 것"이 생길 때 울린다.
- 완료 기준: 앱을 열면 어느 봇이 나를 기다리는지 한 화면에서 보이고, 눌러서 바로 답할 수 있다.

**B5. 일정과 GitHub 트리거** (L)
- 일정: 매시간·매일·평일·매주·cron. 저널에 저장하고 Studio가 떠 있는 동안 호스트 타이머가 실행한다. 놓친 일정은 깨어난 뒤 한 번만 따라잡는다. 봇이 `schedule` 요청으로 제안하면 사용자가 확인해야 켜진다. 가져온 봇의 일정은 꺼진 채 들어온다.
- GitHub: 호스트가 `gh` 로 주기적으로 조회한다. 조건 예: 지정 저장소에서 `bot:<이름>` 라벨이 붙은 이슈, 본문·댓글의 `@<봇 표시 이름>` 언급, 새 PR, CI 실패. 맞으면 해당 봇을 깨우고, 봇의 `reply` 요청을 호스트가 `gh issue comment`/`gh pr comment` 로 게시한다. 클라우드 중계가 없으므로 PC가 켜져 있을 때만 돈다.
- 기존 이슈 동기화(`github_sync.py`, GitHub App)와의 관계: 그쪽은 Workspace 목표로 들어가는 무인 경로다. 개인 사용에서는 `gh` 폴링이 설정 없이 바로 된다. 둘을 한 화면에서 고르게 한다.
- 일정 실행은 기본 읽기 전용이다. 수정이 필요한 일은 B3의 위임을 거친다.
- 완료 기준: "평일 9시에 어제 병합된 변경 요약"이 사람 없이 돌아 봇 대화에 쌓인다. 이슈에 라벨을 붙이면 봇이 그 이슈에 답한다.

**B6. 템플릿, 가져오기, 봇 방** (M)
- 템플릿 10종 이상을 카탈로그에 올린다. 코드 리뷰어, 테스트 작성자, 릴리스 노트, 의존성 점검, CI 실패 분류, 아침 요약 등. 템플릿은 `SOUL.md` 와 꺼진 일정 제안을 담는다.
- 가져오기: Orca 봇 패키지(홈 구조가 거의 같다), Claude Code 서브에이전트(`.claude/agents/*.md`), Agent Skills 폴더. 키·로그인 파일은 건너뛴다.
- 봇 방: 회의실에서 `@이름` 으로 봇을 부르고, 봇이 다른 봇을 부를 수 있다. 지금의 왕명(정규식 분담)을 이것으로 바꾼다. "왕"은 방의 진행자(조정자 봇)로 남긴다.
- 스킬: 봇 홈의 `skills/<이름>/SKILL.md` 를 엔진이 필요할 때 읽게 한다(홈이 실제 폴더이므로 크기 한도 문제가 사라진다 — 초판 P1-2 흡수). 호스트 스킬 등록부와 이중 체계가 되지 않게 하나로 합친다.
- 완료 기준: Orca에서 내보낸 봇을 가져와 대화가 된다. 방에서 두 봇이 서로의 답을 이어 받는다.

### 먼저 확인할 것 (B1 착수 전 짧은 시험)

아래는 코드와 문서만으로는 답할 수 없어 실제 엔진으로 확인해야 한다. 공급자 호출이 생기므로 소유자 승인 사항이다.

1. 각 엔진이 "홈에는 쓰기, 저장소에는 읽기만"을 표현할 수 있는가. Codex는 쓰기 가능 경로를 설정으로 받는다(`codex_inbox.py:342` 의 `writable_roots`). Claude Code와 `agy` 의 추가 디렉터리·권한 인자는 확인이 필요하다.
2. 세션 재개가 봇 대화 용도로 충분히 안정적인가. 지금 재개는 질문 답변을 잇는 데만 쓰인다(`batch_dialogue.py:20-26`).
3. 봇이 프리앰블의 지시대로 요청 파일을 정확한 형식으로 쓰는가. 형식이 틀렸을 때 호스트가 다음 턴에 오류를 돌려주면 고치는가.
4. 위 세 가지는 Codex로 먼저 확인한다(개정 2). `agy` 는 선택 시 동작하는지만 본다. 봇 세션은 일정으로 자주 깨어나 워커보다 호출이 많으므로 `agy` 를 봇 세션의 기본으로 두지 않는다(M-1).

### 정해야 할 것

1. 봇 홈의 위치. 권고: 저널 옆 호스트 데이터 폴더. 저장소 안에 두지 않는다(워커가 건드릴 수 있고 Git에 섞인다).
2. 봇 세션에 `gh` 읽기 명령을 직접 열 것인가, 전부 요청 파일로 할 것인가. 권고: 처음에는 전부 요청 파일. 불편이 확인되면 읽기만 연다.
3. Bot Definition의 다음 버전을 낼 것인가. 권고: 아직 아니다. 홈 구조가 안정된 뒤 `memory/`, 일정 제안, 실행 프로필을 포함해 한 번에.
4. 기존 Workspace의 "역할 봇 배정" 화면을 어떻게 부를 것인가. 권고: "워커 지침"으로 이름을 바꿔 봇과 구분.
