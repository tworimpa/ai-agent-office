# AI Agent Office 단계별 납품 계획

상태: 후속 개발을 위한 제안. 일정 확약·구현 완료·무인 운영 승인을 뜻하지 않는다.
현재 기준: AO-000 main `c82482e`, AO-001 설계/구현 계획 작성 단계.

## 작업 방식과 첫 개발 묶음

공유 인터페이스를 한 구현자가 순서대로 연결하고, 변경 전체를 독립 리뷰하는 방식을 추천한다. 기능별로 작은 commit을 남기되 테스트와 동작이 완결된 묶음으로 PR을 구성한다. 아래 PR 이름은 예정이며 아직 원격 PR을 만들지 않았다.

| 순서 | 예정 변경 묶음 | 시작 조건 | 보여줄 산출물 | 다음 단계 통과 조건 |
|---|---|---|---|---|
| 0 | 실제 worker 연결 확인 | 사용자의 모델 호출 허용, 사용할 CLI 로그인 | Windows/WSL의 읽기 호출 결과와 각 CLI 버전 | 실제 호출/미검증 항목 구분. 실패해도 fake 기반 AO-001 개발은 진행 가능 |
| 1 | AO-001A: 결과 판정 보완 + 저장/필터 (Task 0–2) | 현재 설계·수용 계약 기준 확정 | tasks/runs/events 저장 API, 재시작·원자성·중복/마스킹 테스트 | 오류/중복 입력에서 DB와 attempt가 일관됨. 이 단계만으로 사용자 run 기록 완료를 주장하지 않음 |
| 2 | AO-001B: 소유권·복구 (Task 3) | 저장/필터 API 확보 | 두 프로세스 잠금 시연, owner 사망 후 recovery 판정 | 살아 있는 run 불변, worker 재호출 0회 |
| 3 | AO-001C: 실행 연결 + 조회 (Task 4–5) | 잠금·복구 검증 | 작업 실행 → 종료 → 새 터미널의 tasks/events 조회 시연 | 수용 A01–A14 및 OS/Python CI 4조합 통과 |

여러 PR로 나누면 AO-001A → B → C 순서로 의존성을 명시한다. review/CI 효율상 한 PR로 묶더라도 위 commit 경계와 수용 기준을 유지한다. 최초 구현은 Task 0의 판정 충돌/Git 오류 회귀부터 시작한다.

자세한 파일·함수·테스트: [AO-001 구현 계획](2026-11-06-ao-001.md).
사용자 관점의 명령·JSON·14개 수용 시나리오: [수용 계약](../specs/2026-11-06-ao-001-acceptance.md).

## AO-002: 오피스 관찰 화면과 에이전트 확장

목표는 터미널 조회 정보를 화면에서 확인하는 것이다. 먼저 읽기 화면을 만들고, 작업 실행 버튼은 별도 변경으로 추가하는 순서를 제안한다.

| 묶음 | 구현할 기능 | 시연과 완료 기준 |
|---|---|---|
| AO-002A 관찰 화면 | 작업 보드, agent 역할/엔진 표시, 작업 상세, 순서 있는 이벤트 타임라인 | 작업 선택 시 task/run/attempt/상태/경로 표시. 새 이벤트를 cursor로 받아 중복 없이 갱신. 새로고침 후 같은 작업 복원. 화면을 열어도 worker 실행 0회 |
| AO-002B 엔진 목록 | Claude/Codex 진단 정보, installed/auth/실행 검증 상태를 분리 표시 | '설치됨'만으로 '사용 가능' 표시하지 않음. 미로그인/사용량 오류/CLI 실패를 서로 구분 |
| AO-002C 추가 엔진 | Gemini/Cline/Antigravity별 capability 조사 후 adapter를 한 개씩 추가 | 각 엔진의 공식 headless/구조화 출력/중단·권한 동작을 확인한 뒤 지원 범위 명시. engine별 fake+실제 수용을 분리. 확인되지 않은 기능은 disabled |
| AO-002D Skills 목록 | worker별 설치 skill의 출처·버전·경로·할당 조회 | 어떤 worker에 무엇이 연결됐는지 확인. 화면 조회가 임의 skill 실행/설치로 이어지지 않음 |

화면·API의 기술 선택과 디자인은 이 단계 착수 시 별도 설계한다. AO-001 DB를 브라우저가 직접 수정하게 하지 않는다. API를 추가할 때 stable/candidate의 DB와 포트를 따로 고정한다. 위 묶음을 모두 한 번에 구현하지 않는다.

## AO-003: 질문함과 부재중 기술 결정

질문과 실행 권한 승인을 서로 다른 항목으로 저장한다. 먼저 사람이 답하고 이어가는 흐름을 만들고 그다음 제한된 대리 답변을 붙인다.

| 순서 | 사용자가 할 수 있는 일 | 완료 기준 |
|---|---|---|
| 1. 질문함 | 작업별 질문·선택지·근거를 보고 직접 답변 | 답변이 원래 task/run/question에 연결되고 중복 응답을 거절. 아직 사용하지 않은 답변과 사용된 답변을 구분 |
| 2. 확인 후 이어가기 | 중단 원인과 worker 상태를 보고 이어가기 요청 | engine의 resume 지원을 검증한 경우만 사용. 외부 부작용을 반복하는 노드를 그대로 재실행하지 않음. 미지원 엔진은 명시적 새 작업으로 처리 |
| 3. 부재중 대리 답변 | 사전 허용된 기술 질문을 전문 역할과 검증 역할이 처리 | 정책에 없는 질문은 WAITING_USER. 다른 agent의 답변을 사람의 권한 승인으로 취급하지 않음 |
| 4. 복귀 보고 | 부재중 결정·이유·변경·검증·미결 질문 확인 | 각 결정을 관련 diff와 테스트로 추적. 근거 없는 '해결 완료' 표시 없음 |

질문 감지 방식은 엔진별 조사 대상이다. CLI stdout에서 물음표만 찾아 질문으로 판단하지 않는다. 실제 질문 이벤트를 얻지 못하는 엔진은 질문 자동 처리 지원을 표시하지 않는다.

## AO-004: Agent Office의 자기 개발

첫 시연 과제는 'Agent Office가 자기 저장소의 작은 회귀 테스트/오류 수정을 후보 worktree에서 만들고 검증 보고서를 제시하는 것'으로 제안한다.

1. 사용자가 개선 과제를 입력하고 현재 stable 버전/후보 기준 commit을 고정한다.
2. 후보 전용 worktree/DB/프로세스에서 수정·테스트·독립 리뷰를 수행한다.
3. 결과 화면에서 diff, 테스트, 예상 영향, 미해결 사항을 제시한다.
4. 사용자의 명시적 승인 후에만 머지 또는 버전 승격을 수행한다.
5. 이전 실행 버전과 데이터를 보존하고 되돌리기 절차를 검증한다.

완료 기준은 후보의 실패/중단이 stable 작업과 DB를 변경하지 않는 것, 변경 결과와 사람의 승인을 추적할 수 있는 것이다. '자가 개발'은 무조건적인 자기 승인·자동 배포로 정의하지 않는다.

## 단계별 실제 시연 문장

- AO-001: “작업을 시킨 뒤 터미널을 닫아도 어디까지 했는지 다시 확인할 수 있다.”
- AO-002: “화면에서 역할별 작업과 실패 원인, 실행 이력을 볼 수 있다.”
- AO-003: “막힌 질문에 답해 이어가고, 허용한 기술 판단은 부재중 처리 내역으로 확인할 수 있다.”
- AO-004: “Agent Office에 자기 개선을 시키면 검증된 후보와 변경 보고서를 받아 검토할 수 있다.”

## 일정과 변경 관리

현재는 달력 날짜나 작업 시간으로 완료를 약속하지 않는다. 첫 AO-001A 구현에서 저장 API 규모와 OS 차이를 확인한 뒤 나머지 묶음의 추정을 갱신한다. 각 묶음의 시작/완료/막힌 이유는 위 수용 기준으로 보고한다. 요청 범위가 늘면 영향을 받는 묶음과 수용 기준을 먼저 갱신한다.
