# 4단계 구현 계획 · 오피스 보기

작업실 사용자가 어느 에이전트가 무엇을 맡았는지 보고, 응답이 필요한 자리에서 원래 실행 상세로 이동한다. [제품 구상](../../product-vision.md)

| 작업 | 설계 | 완료 기준 |
| --- | --- | --- |
| 실행 기록 조회 | 실행 호스트의 저널에서 담당 역할·엔진, 현재 단계, 대기 중인 기술 질문·권한 요청을 읽는다. 병렬 작업은 실제 자식 실행 ID를 사용한다. | 같은 엔진의 두 배정을 구분하고, 계획 모드·중지·실패·재시도에서 실행하지 않은 역할을 활동 중으로 표시하지 않는다. |
| 로컬·원격 연결 | 기존 SSH 저널 확인을 사용하는 전용 조회 API를 추가한다. 화면은 호스트별로 새로 고치고 접속이 끊기면 마지막 확인 시점을 표시한다. | 한 호스트의 장애 중에도 다른 호스트를 볼 수 있다. 조회로 작업을 시작하거나 결정을 보내지 않는다. |
| 오피스 화면 | 역할별 캐릭터와 작업 카드를 배치하고, 말풍선에 요청 종류와 내용을 표시한다. 클릭·키보드 선택은 호스트와 실행 ID를 보존한다. | 원격 자식의 캐릭터에서 해당 자식 상세로 바로 이동한다. 좁은 화면과 빈 작업실에서도 상태가 명확하다. |
| 검증 | 모의 CLI와 격리된 두 작업실에서 실행, 대기, 답변 이후 상태 변화를 확인한다. | Windows·Ubuntu 테스트와 실제 브라우저에서 로컬·원격 조회 및 상세 이동을 검증한다. |

이번 변경은 오피스 보기에 집중한다. Office 자체 개선과 안정 버전 승격은 별도 개발 범위다.

## 상태와 이동의 기준

에이전트 자리의 식별자는 호스트 저널, 실제 실행 ID, 역할의 조합이다. 병렬 부모는 자식을 묶는 단위이므로 자리에 부모 작업명을 함께 표시하고, 클릭 대상은 자식의 실행 ID로 둔다. 계획 모드는 개발자만 배정한다. 테스트 단계는 저장소 테스트 실행으로 표시한다.

요청 수에는 현재 시도와 역할이 일치하고 원래 작업자가 여전히 응답을 기다리는 기술 질문과 권한 요청을 반영한다. 부재중 위임으로 근거를 확인하는 동안에는 위임 상태로 표시한다. 위임이 종료되거나 검증을 마치지 못해 사람에게 넘어간 질문은 응답 대기에 포함한다. 오래된 이력에는 남아 있는 기록으로 확인할 수 있는 단계만 표시한다.

호스트별 진행 실행과 최근 종료 실행 8개를 대상으로 응답 필요, 진행 중, 최근 기록 순으로 페이지를 구성한다. 전용 조회는 같은 SQLite 읽기 트랜잭션의 상태를 사용한다. 원격 호스트는 지정된 SSH 피어와 저널이 일치할 때만 해당 호스트의 합계와 링크를 제공한다.

| 검증 경로 | 확인할 내용 |
| --- | --- |
| [상태 조회](../../../tests/test_office_state.py) | 역할·최신 시도·실제 요청 연결, 병렬 자식, 페이지와 일관된 합계 |
| [작업실 HTTP](../../../tests/test_office_http.py) | 로컬/원격 API와 실제 모의 Cline 세션의 질문 → 권한 요청 → 종료, 올바른 상세 주소 |
| [화면](../../../tests/web/office.test.mjs) | 클릭·키보드 이동, 호스트 필터, 단절·복구와 페이지 전환 |

브라우저 시험은 Windows Edge와 기본 OpenSSH를 통해 같은 PC의 WSL Ubuntu Studio를 연결한다. 제공자 역할에는 모의 CLI를 사용한다. 이 시험의 실행 상태는 Studio가 관찰한 단계와 요청을 나타낸다.
