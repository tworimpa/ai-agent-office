# 3단계 구현 계획 · 역할별 스킬과 제한된 병렬 작업

로컬 또는 SSH로 연결한 호스트에서 역할에 스킬을 지정하고 독립적으로 검증할 하위 작업을 한 요청으로 맡긴다. 원래 작업에서 각 결과를 다시 찾을 수 있어야 한다. [제품 구상](../../product-vision.md)

| 작업 | 구현 결정 | 검증 기준 |
| --- | --- | --- |
| 스킬 등록·배정 | 호스트 저널에 이름·버전·본문 해시를 저장한다. 개발자·리뷰어·부재중 전문가·독립 검증자는 각자 지정된 지침만 받는다. | 같은 이름의 새 버전을 등록해도 기존 실행에서 사용한 버전과 지침은 보존된다. 다른 호스트의 ID와 잘못된 역할은 거부된다. |
| 하위 작업 배정 | 사용자가 독립 작업의 목표·담당 엔진·폴더를 정한다. 한 호스트에서 같은 기준 커밋을 고정하고 분리된 worktree에서 제한된 개수만 동시에 실행한다. | 동시에 실행되어도 파일을 덮어쓰지 않고, 중복 접수·중지·프로세스 중단 시 새 실행을 임의로 재생하지 않는다. |
| 인계와 결과 집계 | 원래 요청과 하위 작업의 목표, 스킬, 기준 커밋을 연결한다. 자식별 변경 파일·diff·테스트·리뷰와 실패·중단 상태를 부모 상세에서 조회한다. | 일부 실패를 전체 성공으로 표시하지 않고, 재접속 후 같은 부모·자식 ID와 근거를 확인할 수 있다. |
| 로컬·원격 검증 | 기존 SSH 저널 확인과 작업실 권한 경계를 사용한다. | Windows와 Ubuntu에서 모의 CLI로 기본 실행과 병렬 실행을 검증하고 브라우저에서 실제 조작 경로를 확인한다. |

이 단계는 사용자가 분리한 독립 작업을 다룬다. 변경 반영은 각 worktree의 결과를 사람이 검토한 뒤 결정한다.

## 실행과 복구

요청 ID, 부모·자식 관계, 선택한 역할별 스킬 버전, 하위 작업 순서와 각 엔진을 한 트랜잭션에 기록한다. 작업실은 한 부모에 2~4개의 하위 작업을 접수하며, 같은 저널의 부모들이 두 개의 병렬 실행 슬롯을 공유한다. 다음 자식은 빈 슬롯이 생기면 브라우저 접속 여부와 관계없이 시작한다. 부모를 중지하면 대기 작업을 취소하고 이미 시작한 자식의 종료를 확인한다.

원본 요청 본문은 실행기 메모리에서 자식에게 전달하고 이력에는 기존 마스킹 규칙을 적용한다. 접수 응답이 유실된 경우 같은 ID로 기존 부모와 자식을 조회한다. 소유자가 비정상 종료된 뒤에는 남은 원문을 추정해 작업을 재실행하지 않는다. 자식은 각각 자신의 worktree·테스트·리뷰 결과를 소유하며, 부모의 완료 상태는 이 결과의 집계다.

| 검증한 동작 | 테스트 |
| --- | --- |
| 스킬 버전의 불변성·중복 접수·순서와 네 역할 간 지침 분리 | [스킬 테스트](../../../tests/test_role_skills.py) |
| 슬롯 제한, 독립 worktree, 부모 중지·소유자 종료, 접수 롤백·소유권 인계 | [실행기 테스트](../../../tests/test_team_runs.py) |
| 원격 응답 유실 후 재접수, 성공·실패 증거 동시 유지, 원본 체크아웃 보존 | [Studio 통합 테스트](../../../tests/test_team_http.py) |
| 원격 저널·버전·폴더·엔진·자식별 결과 일치 확인 | [원격 응답 테스트](../../../tests/test_team_wire.py) |
| 부모에서 자식 결과 열기와 원래 실행으로 복귀, 재접속 | [화면 테스트](../../../tests/web/studio.test.mjs) |

Windows Edge에서 로컬 Studio와 OpenSSH로 연결한 같은 PC의 WSL Ubuntu Studio를 검증했다. 각 호스트에서 Markdown 스킬 두 개를 등록하고 두 자식을 시작했다. 한 자식의 테스트·리뷰 성공과 다른 자식의 테스트 실패를 부모 화면에서 확인하고 부모 주소를 다시 열어 같은 결과를 복원했다. 코딩 에이전트는 모의 CLI 프로세스를 사용했다.
