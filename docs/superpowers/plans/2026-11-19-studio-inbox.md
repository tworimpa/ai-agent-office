# 3단계 구현 계획 · 협업 요청함

작업자가 질문하거나 도구 사용 허가를 기다리면 사용자가 로컬 작업실에서 판단한다. 원격 실행의 요청과 결정은 그 실행을 소유한 호스트에 기록한다. [제품 구상](../../product-vision.md)

| 작업 | 구현 결정 | 완료 기준 |
| --- | --- | --- |
| 요청 저널 | 실행·역할·엔진·세션에 요청을 연결한다. 기술 질문의 답변과 권한 요청의 일회성 승인·거절을 다른 입력으로 저장한다. | 두 탭의 동시 결정은 하나만 채택하고, 접수 응답 유실 후 같은 결정의 재전송은 기존 기록을 반환한다. |
| 실행기 연결 | 요청함을 사용하는 실행에서는 지원하는 제공자 프로토콜의 실제 세션을 유지한다. 결정은 요청을 생성한 세션에만 전달한다. | 답변 후 원래 작업이 이어지고, 거절한 도구는 실행되지 않는다. 중지·시간 초과·복구 대상이 된 세션에는 늦은 결정을 보내지 않는다. |
| 로컬·원격 화면 | 호스트의 대기 요청과 작업별 결정 내역을 표시한다. 요청 종류와 실제 대상·담당자를 확인한 뒤 응답한다. | 요청 ID와 실행 ID가 일치하는 호스트에서만 결정을 접수하고, 재접속 시 대기·결정·전달 상태를 복원한다. |
| 검증 | 모의 CLI와 독립된 작업실 두 개에서 실제 프로세스·HTTP·SSH 규약·화면을 확인한다. | 같은 실행에서 질문과 승인 또는 거절을 처리하고 결과를 확인한 뒤 Windows·Ubuntu CI를 통과한다. |

이 단계는 사용자가 직접 처리하는 요청에 집중한다. 부재중 자동 대리 판단과 사용자 전용 권한의 위임은 후속 범위다.

## 전달과 복구

1. 호스트는 요청 ID와 실행·역할·시도·엔진을 기록한다. 요청을 만든 작업자가 대기할 때만 답을 받는다. 한 실행에 최대 100건의 요청을 기록하며 호스트 목록은 대기 중인 요청을 오래된 순서로 최대 100개 표시한다.
2. 동일 ID에 동일한 결정이 다시 오면 기존 결정을 반환한다. 다른 결정으로의 덮어쓰기, 다른 호스트·실행을 통한 응답, 기술 답변으로 도구 권한을 승인하는 시도는 거부한다.
3. 작업자는 전송 직전에도 중지·만료 여부를 검사한다. 원래 제공자 세션의 확인 응답을 받은 후 전달 시각을 기록한다. 중간에 세션을 잃으면 저장된 사용자 결정을 보존하고 실제 전달은 미확인으로 남긴다.
4. Codex는 요청함을 켠 실행에서 app-server 스레드와 파일 변경 항목을 사용한다. Cline은 원본 파일 도구 입력과 역할 범위를 재검사한다. Gemini는 기존의 추가 권한 거부 정책을 따른다. Claude Code와 Antigravity는 원래 대화 UUID를 명시하고 동일한 역할·폴더·권한 설정으로 질문에 이어간다. [Codex app-server 승인 규약](https://developers.openai.com/codex/app-server/#approvals) · [Claude Code CLI](https://code.claude.com/docs/en/cli-reference) · [Antigravity 헤드리스 규약](https://antigravity.google/docs/cli/headless/)

2026년 11월 19일 Windows Edge에서 로컬 작업실과 Windows 기본 OpenSSH를 경유한 같은 PC의 WSL Ubuntu 작업실을 열었다. 모의 Cline 프로세스가 먼저 기술 질문을 보내고 답변 수신 뒤 파일 읽기 권한을 요청했다. 로컬에서 승인한 파일은 읽혔고, 원격에서 거절한 읽기의 호출 횟수는 0이었다. 원격 거절 접수 직후 응답을 유실시킨 뒤 같은 주소로 돌아와 재전송 없이 원래 두 결정의 전달 기록을 확인했다. Codex app-server와 다른 엔진의 대화 규약은 별도 모의 프로세스로 검사했다. 인증된 벤더 CLI 실작업은 이번 검증 범위 밖이다.
