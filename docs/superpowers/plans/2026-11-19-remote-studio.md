# 2단계 구현 계획 · 원격 폴더와 실행 재연결

**목표**는 로컬 작업실에서 실행 호스트와 폴더를 고르고, SSH 연결이 끊겨도 원격에서 진행한 같은 실행의 결과를 다시 여는 것이다. [제품 구상](../../product-vision.md)의 원격 실행부터 구현한다.

| 작업 | 설계 | 통과 기준 |
| --- | --- | --- |
| 호스트 연결 | 로컬 운영자가 SSH 별칭, 원격 루프백 포트, 원격 저널 ID를 지정한다. OpenSSH는 기존 인증과 호스트 키 검증을 사용한다. | 허용된 작업실 API만 전달하고, 연결 실패나 저널 교체 시 다른 실행기로 전환하지 않는다. |
| 원격 작업 소유 | 원격 작업실이 폴더 등록·경로 검증, worktree 생성, 실행과 중지, SQLite 기록을 담당한다. | 로컬에 원격 경로가 없어도 작업을 시작한다. 응답이 유실돼 같은 요청을 다시 보내도 실제 실행은 하나다. |
| 화면과 복구 | 호스트마다 작업공간·실행 목록을 조회한다. URL에는 호스트·실행 ID를 보관하고 접수 재확인도 같은 호스트로 보낸다. | 단절을 실행 실패와 구분한다. 다시 연결하거나 페이지를 열면 같은 작업의 상태·테스트·diff·리뷰를 표시한다. |
| 통합 검증 | 분리된 두 작업실, 끊을 수 있는 전송 경로, 모의 CLI로 실제 프로세스와 원본 체크아웃을 확인한다. | 실행 중 단절·접수 직후 응답 유실·재접속·중지·잘못된 저널을 검증하고 Windows·Ubuntu CI를 통과한다. |

원격 작업실은 SSH 연결과 독립된 프로세스로 먼저 실행한다. 각 호스트의 작업 이력과 파일은 해당 호스트에 보관한다. 로컬 화면을 다른 기기에 공개하는 기능과 추가 CLI 엔진 연동은 별도 개발 범위다.

## 접속이 끊기는 시점별 처리

| 시점 | 재연결 후 화면과 실행기의 동작 |
| --- | --- |
| 작업을 보내기 전 | 호스트가 연결되면 원격 작업공간을 다시 조회하고 사용자가 시작한다. |
| 전송 후 접수 응답을 받기 전 | 브라우저에 기록한 호스트·실행 ID로 먼저 조회한다. 원격에 이미 접수됐으면 같은 상세를 열고, 접수 기록이 없으면 사용자가 같은 ID로 재전송할 수 있다. |
| 실행 중 또는 완료 뒤 | 원격 프로세스가 독립적으로 진행한다. 화면은 단절을 알리고, 복구되면 원격 저널의 최신 상태·결과 스냅샷을 읽는다. |
| 포트가 다른 저널을 가리킬 때 | 피어가 요청 경로에 포함된 저널 ID를 확인하고 작업을 받기 전에 거부한다. 전송 측도 응답 헤더의 저널 ID를 확인한다. |

단계 이벤트 원본은 원격 SQLite에 남는다. 이번 구현의 재연결 단위는 실행 상세 스냅샷이며, Core에 원격 이벤트를 순번별 복제하는 작업은 후속 범위다. [전송 테스트](../../../tests/test_studio_ssh.py) · [단절·재접속 통합 테스트](../../../tests/test_remote_studio.py) · [화면 테스트](../../../tests/web/studio.test.mjs)

## 2026년 11월 19일 실행 검증

Windows Edge의 로컬 작업실에서 Windows 기본 OpenSSH와 테스트 전용 SSH 서버를 거쳐 같은 PC의 WSL Ubuntu 작업실에 접속했다. 임시 키와 별도 SSH 설정으로 인증했고, 원격 폴더 등록은 HTTP 201, 작업 접수는 HTTP 202를 반환했다. 실행 중 전달을 끊고 창을 떠난 뒤 원격 작업을 마치게 했다. 연결 복구 후 같은 URL에서 테스트 2개 통과, 리뷰 승인, 변경 diff를 확인했다. 모의 개발 CLI는 1회 실행됐고 로컬 저널의 실행 수는 0이었다.

자동 통합 테스트에서는 원격이 이미 접수한 응답을 버리고 로컬 작업실을 재시작한 경우에도 같은 ID를 재사용하는지 확인한다. 실제 물리 서버의 네트워크·SSH 정책과 벤더 CLI 인증은 이 검증의 범위 밖이다.
