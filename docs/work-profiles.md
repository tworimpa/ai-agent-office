# 작업 방식, 사용량과 캐릭터 프로필

Workspace에서 조정자에게 원하는 결과를 입력한다. 수정과 검증을 맡길 때는 파일 수정과 장시간 목표를 선택한다. **자동**은 읽기 전용 의뢰에 빠른 확인, 수정 의뢰에 균형 개발을 적용한다. 원본 실패를 재현해야 하는 목표의 Codex 리뷰어에는 호스트에서 확인한 심층 추론 강도를 우선한다. 최초 배정에서 엔진의 모델 목록을 확보하지 못한 자동 의뢰는 CLI 기본값으로 시작한다.

## 배정과 위임

빠른 확인은 사전 개발·검토 회의를 생략하고 조정자가 개발 담당자에게 바로 배정한다. 읽기 전용 의뢰의 자동 모드와 Workspace에서 상속한 빠른 확인도 같은 경로를 쓴다. ‘계획을 보고 시작’을 직접 선택하면 계획 확인이 우선한다. 수정 작업의 테스트와 독립 리뷰, 담당자가 작업 중 보내는 질문과 권한 요청은 각자의 기존 단계에서 처리한다.

작업실 설정의 작업 방식에서 역할별 모델·강도와 목표 예산을 지정할 수 있다. 개별 의뢰의 고급 옵션은 해당 목표에만 적용된다. 캐릭터는 이 Workspace의 역할 자리와 연결되며 엔진·모델을 교체해도 이전 대화와 근거는 그 자리에 남는다. 선택한 호스트에서 모델 목록을 갱신한다. 조회에는 모델 턴이 필요하지 않다. 요청 설정을 명시했는데 호스트에서 지원을 확인할 수 없으면 접수 시 알려준다. 엔진별 옵션과 실제 관측 가능 범위는 [공급자 지원표](provider-profiles.md)에서 확인할 수 있다.

역할별 대체 목록은 한도에 도달한 경우에만 사용하며 순서와 대상은 작업을 시작할 때 고정한다. 같은 CLI의 계정 별칭은 이미 로그인된 계정을 설명하는 표식이다. 계정이나 자격증명을 바꾸는 설정은 아니다. 별도로 재작업 심층 추론을 위임할 수 있다. Codex 개발자가 변경 파일 또는 실패 검사를 짚어 `다음 가설:`을 남기고 같은 실패가 검증에서 반복된 경우, 확인된 상위 추론 강도를 다음 구현 시도 한 번에 적용한다. 환경·검증 범위 변경 및 미결 제품 결정은 구분해 기록한다. 기존 재시도 횟수와 제품 결정·도구 권한 절차를 따른다.

## 아침에 결과 확인하기

브리핑에서 질문 또는 후보를 누르면 원래 요청과 검증 근거를 연다. **지난 방문 이후**는 이 호스트와 Workspace의 방문 시각을 공유한다. 두 데스크톱에서 같은 작업을 이어 볼 수 있다. 자동 새로고침은 방문 시각을 옮기거나 공급자 호출을 시작하지 않는다.

**작업 프로필과 사용량**에는 역할·단계·시도, 요청한 모델과 공급자가 보고한 모델을 표시한다. 재라우팅, 대체 배정, 대기·재개에는 시각과 이유가 있다.

- 목표 토큰은 누적 통지의 중복을 제거해 호출 단위로 합산한다. 캐시·추론 토큰은 각 내역의 일부다. 일부 호출만 공급자 수치를 보고하면 부분 합계로 표시한다. pytest의 수행 시간은 모델 토큰과 별개다.
- 문맥 창 크기와 공급자가 보고한 직전 응답의 토큰을 표시한다. 직전 응답을 사용하는 점유·여유 값은 추정치다.
- 계정 한도는 공급자가 보고한 구간별 비율과 갱신 시각이다. 계정 지문이나 명시된 별칭으로 확인되는 풀은 최근 스냅샷을 사용한다. 여러 호스트의 비율을 더하지 않는다. 출처가 불확실한 계정은 별도로 남는다.
- 목표 예산은 사용자가 정한 시간·시도·토큰이다. 토큰 한도는 다음 호출 경계에서 집행되므로 이미 시작된 한 번의 호출이 잔여량을 초과할 수 있다. 앞선 호출의 최종 소비량이 불명확하면 새 유료 호출 전에 중단한다. 예산 정책은 장시간 목표에 적용되며 일반 읽기 전용 의뢰에도 실제 호출 내역은 남는다.

한도 대기는 안전한 단계 경계에 저장된다. 기본 정책에서는 새 공급자 응답이 같은 계정과 한도 풀의 사용 가능 상태를 확인한 뒤 재개한다. 갱신 예정 시각만으로 다시 실행하지 않는다. 이미 실행된 외부 작업의 완료 여부가 불명확하거나 복합 단계 안에서 안전한 재시작 지점이 없으면 원래 실행에서 중단 사유를 확인한다.

## 육각형 읽기

초상화를 누르면 대화가 먼저 열린다. **캐릭터 프로필과 작업 근거**를 펼치면 전문 역할, 기간, 축별 표본과 원래 기록이 보인다. 최근 90일의 가장 최근 배정 120개 안에서 한 실행이 한 축에 낼 수 있는 표본은 하나다. 같은 실행에서 가장 강한 근거를 쓰며, 해당 축에 근거가 있는 실행이 세 개 이상일 때 강도 중앙값을 1~5 눈금으로 표시한다. 근거가 없는 축에는 점수를 매기지 않는다.

| 축 | 기록에서 확인하는 사실 |
|---|---|
| 분석 | 개발자의 기준 커밋 실패, 리뷰어의 변경 요청, 조정자의 승인된 범위·계획 |
| 구현 | 개발자의 파일 변경 후보(2), 검증 통과(3), 독립 리뷰 승인(4), 사용자 채택(5) |
| 검증 | 개발 후보에서 최초 실패가 해소된 검사(4), 독립 리뷰까지 완료한 검사(5), 리뷰어가 확인한 검사 통과 후보(4) |
| 리뷰 | 실제 후보의 독립 리뷰(3), 사용자가 채택한 검토 후보(4), 변경 요청 후 다른 후보 승인(5) |
| 프로젝트 이해 | 본인이 참여한 승인 계획의 Workspace 기준과 대응하는 통과 결과(4) |
| 협업·인계 | 원래 요청의 답변이나 추가 지시 전달(3), 전달 후 같은 시도에서 후보 승인 또는 지시가 연결된 승인 계획 버전(4) |

눈금은 기록의 강도이며 업무 난이도·모델의 보편적인 성능을 뜻하지 않는다. 동일 유형·역할 안에서 공급자가 확인해 준 같은 조합의 종료 실행만 비교한다. 재라우팅된 실행과 조합이 불명확한 실행은 단일 조합 실적에서 제외한다. 목표 채택·재작업·실제 작업 시간은 목표의 결과이고 토큰은 해당 역할의 보고량이다. 소수 사례는 표본 수와 함께 읽는다. 이전 저널에서도 실제 테스트·후보는 열 수 있으며 당시 수집하지 않은 모델·토큰을 소급해 채우지 않는다.

## 대표 실행의 근거

Windows 설치판의 예제에서 설정 파일 재오픈 실패를 재현한 뒤 파일을 수정했다. 처음 작성된 두 테스트가 통과했고 별도 리뷰어가 후보를 승인했다. 개발자에게 요청한 조합은 `fixture-codex / medium`이었고 모의 공급자가 `fixture-codex-routed`로 전환했다. 중복 통지를 보냈을 때도 개발자 합계는 300토큰이었으며 리뷰어의 사용량은 미확인으로 남았다. 별도 한도 시험에서는 같은 실행의 기준 검사를 보존하고 승인된 새 한도 근거가 들어온 뒤 파일을 한 번만 수정했다. [화면](evidence/work-profiles/character-windows.png) · [후보·검증·사용량 기록](evidence/work-profiles/morning.json)

설치판 CI에는 `comparison-evidence/handoff/morning-work-profile.json`, 일반·좁은 창의 사용량 화면, `quota-restart/receipt.json`이 남는다. 코딩·리뷰 CLI는 결정적인 테스트 대역이고 Git과 pytest, Studio 중지·재시작, 설치판 창은 실제로 실행한다. 실제 공급자 확인 범위는 [호스트별 메타데이터 검증](provider-profiles.md)에서 확인할 수 있다.
