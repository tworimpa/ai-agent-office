# AI Agent Office 제품 구상

2026년 11월 19일 · 제품 방향 제안 · 구현 기준점 `main`의 `ccc6fb9`

**AI Agent Office는 사용자가 여러 코딩 에이전트에게 일을 맡기고, 로컬 PC와 원격 호스트에서 진행되는 작업을 한곳에서 확인하는 개인 개발 작업실이다.** 사용자는 작업공간을 고르고 원하는 결과를 적는다. 자리를 비웠다가 돌아왔을 때도 어떤 파일이 바뀌었는지, 무엇으로 검증했는지, 지금 어떤 판단이 필요한지 알 수 있어야 한다.

첫 목표는 **Windows와 Linux에서 여러 로컬 폴더를 등록하고, 작업 하나를 시작해 사람의 검토까지 마치는 경험**이다. 이를 바탕으로 원격 실행과 다섯 엔진 지원을 넓힌다. 코드와 작업 이력은 사용자가 선택한 환경에서 관리하고, 모델 호출과 사용량은 선택한 CLI의 서비스 조건을 따른다.

## 사용자가 보는 작업실

예를 들어 사용자가 “주문 목록에서 취소 주문을 숨기고 기존 주문 테스트로 확인해 줘”라고 요청한다. 사용자는 다음 순서로 일한다.

1. **맡기기.** ‘주문 서비스’ 작업공간에서 요청을 입력한다. 구조 설명에는 ‘직접 맡기기’를, 파일 수정에는 ‘개발·검증 맡기기’를 선택한다. 기본 프로필에 담당 역할과 엔진, 작업 폴더, 테스트가 지정되어 있어 변경할 때만 상세 설정을 연다.
2. **응답하기.** 목록 위에는 ‘내 응답 필요’가 보인다. “취소 주문을 내역 화면에도 숨길까요?”라는 알림을 누르면 원래 요청과 해당 질문이 함께 열린다. 사용자가 “목록에서만”이라고 답하면 그 결정이 작업 이력에 남는다.
3. **검토하기.** 결과 화면에서 수정한 파일과 diff, 실행한 테스트와 결과, 리뷰 의견을 함께 본다. 테스트가 실패했다면 실패한 명령과 마지막 시도를 확인한다. 작업자가 답변을 끝낸 시점, 검증을 마쳐 사람이 검토할 시점, 사용자가 요청한 반영 단계는 각각 표시한다.

flowmux에서는 여러 작업공간 중 응답을 기다리는 곳을 알려 주고 알림을 누르면 해당 세션으로 돌아간다. Office도 이 짧은 동선을 채택한다. 첫 화면에는 새 작업, 진행 중, 응답 필요, 검토 대상을 둔다. 터미널과 상세 로그는 작업 안에서 연다. 선택형 ‘오피스 보기’에서는 실제 실행 상태로 캐릭터와 말풍선을 표시하고, 캐릭터를 누르면 같은 작업 상세가 열린다. ## 작업공간과 여러 폴더

작업공간(workspace)은 관련 폴더와 작업, 역할 프로필을 묶는 단위다. 각 폴더에 별칭, 호스트, 그 호스트에서의 경로, 용도를 지정한다. 작업을 시작할 때에는 주 폴더 하나와 필요한 추가 폴더, 각각의 읽기·수정 범위를 선택한다.

| ‘주문 서비스’의 폴더 | 실행 위치 예시 | 작업에서 맡는 일 |
| --- | --- | --- |
| `web` | Windows PC의 `D:\dev\shop\web` | 목록 화면 수정 |
| `contracts` | 같은 PC의 `D:\dev\shop\contracts` | 같은 저장소의 응답 규격 참조 |
| `api` | Linux 서버의 `/srv/dev/shop-api` | 별도 저장소에서 API 테스트 |

- **같은 저장소**의 `web`과 `contracts`는 같은 실행 worktree 안의 상대 경로로 옮겨 연결한다. 그래야 작업자가 수정 중인 화면과 같은 버전의 규격을 읽는다.
- **다른 저장소**를 수정할 때에는 저장소별 기준 커밋과 worktree를 기록한다. 일반 문서 폴더는 우선 읽기 자료로 다룬다. 실행 전 어댑터가 요청한 폴더 범위를 표현할 수 있는지 확인하고, 불가능하면 지원되는 폴더 구성으로 작업을 나눈다.
- **다른 호스트**의 `api`에서 검증해야 할 때에는 같은 상위 작업 아래 Linux 실행을 배정한다. 기준 커밋, 확인할 규격이나 패치, 테스트 명령을 넘기고 결과를 원래 작업에 연결한다. 양쪽 파일을 자동 동기화할 필요 없이 어떤 버전을 검증했는지 추적할 수 있다.

## 실행 위치와 연결 복구

| 구성 | 맡는 일 |
| --- | --- |
| 작업 화면 | 요청 입력, 진행 조회, 질문 답변, 결과 검토 |
| Office Core | Python·LangGraph로 단계와 역할을 배정하고 작업·실행·결정 이력을 연결 |
| 호스트별 실행기 | 자기 호스트에서 프로세스·worktree·테스트를 관리하고 실행 ID와 순번이 있는 이벤트를 보고 |
| 엔진 어댑터 | 제공자별 입력·출력과 세션 기능을 변환. 각 CLI가 자체 추론과 도구 호출을 수행 |

로컬 설치에서는 Core와 실행기를 같은 PC에 둔다. Windows 네이티브, Linux, WSL은 각각 경로와 실행파일을 가진 별도 환경으로 선택한다. **원격 열람**은 다른 기기에서 Core의 작업 화면에 접속하는 기능이고, **원격 실행**은 Core가 다른 호스트의 실행기에 일을 맡기는 기능이다. 두 기능은 각각 접근 주체와 권한을 설계한 뒤 제공한다. 현재 observer의 접속 범위는 로컬 루프백이다. 원격 실행기는 자신의 이벤트를 전송하고 Core가 기록하므로 호스트끼리 SQLite 파일을 공유할 필요가 없다.

실행 중 창을 닫아도 실행기가 프로세스를 보유한다. 재접속 시 실행 ID와 마지막 이벤트 순번으로 누락분을 읽는다. 연결이 끊긴 사이 명령이 수행됐는지 불명확하면 복구 필요로 표시하고 실행기의 기록을 먼저 확인한다. 중지 버튼을 누르면 ‘중지 요청 중’, 종료가 확인되면 ‘중지됨’을 표시한다. 실행 중인 프로세스에 다시 연결하기, 제공자 대화를 재개하기, 새 실행으로 다시 시도하기는 각각 다른 조작이다.

작업공간에서 동시 실행 수와 실행 시간, 재시도 횟수를 제한할 수 있게 한다. 사용량은 제공자가 돌려준 값과 측정 시점을 표시하고, 값을 제공하지 않은 실행은 ‘알 수 없음’으로 남긴다.

## 다섯 코딩 에이전트와 역할

| 엔진 | 현재 Office에서의 위치 | 다음에 확인할 항목 |
| --- | --- | --- |
| Codex | 기본 개발자 | Windows 네이티브 파일 도구, 양방향 세션의 질문·재개 |
| Antigravity CLI | 기본 리뷰어 | 지정 실행파일로 읽기·리뷰 재현, 대화형 연결에서 권한 요청 처리 |
| Claude Code | 기존 어댑터를 명시적으로 선택 | 각 OS의 파일 작업, 스트리밍 이벤트와 기존 세션 재개 |
| Gemini CLI | 연동 후보 | 읽기 전용 작업부터 확인한 뒤 구조화 출력과 질문 전달 검증 |
| Cline CLI | 연동 후보 | CLI 실행의 권한 처리, 추가 폴더와 중지·재개 검증 |

지원 표시는 **호스트·실행파일 버전·연결 방식·검증 시점**에 귀속한다. 설치 감지, 인증 정보의 확인 가능 여부, 실제 파일 작업, 실시간 출력, 질문, 권한 요청, 중지, 재개, 다중 폴더를 개별 항목으로 기록한다. 근거가 없는 항목은 ‘미검증’으로 둔다. 제공자 전용 인터페이스와 ACP(Agent Client Protocol)는 세션 제어 후보로 평가하고, MCP는 역할에 필요한 도구와 자료를 연결하는 데 쓴다.

역할 프로필에는 엔진, 지침, 스킬과 버전, 도구, 폴더 범위, 테스트 명령을 묶는다. 단순한 질문은 한 역할이 처리하고, 독립 리뷰나 서로 다른 호스트의 작업이 필요할 때 역할을 추가한다. 인계할 때 원래 요청, 완료 조건, 제약, 기준 커밋, 변경 파일과 검증 결과를 다음 담당자에게 전달한다.

## 질문, 승인, 부재중 인계

기술 질문과 권한 승인은 서로 다른 이벤트로 기록한다. 예를 들어 “주문 테스트는 어느 명령으로 실행하나?”는 프로젝트 지침에서 근거를 찾을 수 있다. 사용자가 미리 위임한 범위라면 전문 역할이 답을 제안하고 독립 검증자가 확인한 뒤, 답변 기능이 검증된 원래 세션으로 돌려보낸다. 요구사항을 바꾸는 선택이 모호하거나 인증이 만료되면 사용자 요청함에서 기다린다.

배포나 권한 확대는 사용자가 판단한다. 제품 작업자는 직접 커밋·푸시·머지하지 않는다. 이 저장소 유지보수에 적용되는 소유자의 PR·CI·머지 승인은 별도 범위를 갖는다. worktree는 Git 작업 경로를 나누며, 파일·프로세스·네트워크 접근은 실행 환경의 권한에 따른다. [프로젝트 지침](../AGENTS.md) · [설계 결정](decisions.md)

복귀 보고에는 완료한 일, 대리 판단의 질문·답·근거·적용 정책, 남은 결정, 변경 파일과 테스트 결과를 모은다. 사용자가 세션을 직접 조작할 때에는 입력 제어권을 넘기고 자동 입력을 멈춘다.

## 제안하는 개발 순서와 완료 기준

| 순서 | 사용자에게 열리는 기능 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 1. 로컬 작업실 | 폴더 등록, 화면에서 작업 시작·중지, 실행 상세와 결과 확인 | Windows 네이티브와 Linux에서 같은 저장소의 두 폴더로 작업한다. 원본 체크아웃 보존, 창을 다시 열어 같은 실행 확인, 중지·종료 구분을 시험한다. 실 CLI의 파일 변경·테스트·리뷰 결과를 환경별로 기록한다. |
| 2. 원격과 엔진 확대 | 다른 기기에서 열람, 원격 호스트에서 실행, Gemini·Cline 선택 | 원격 연결이 끊겼다가 돌아와도 실행은 하나이며 이벤트와 결과가 이어진다. 다섯 엔진의 지원 항목과 미검증 항목을 선택 화면에서 확인한다. |
| 3. 협업과 요청함 | 역할별 스킬, 질문·승인, 제한된 병렬 실행, 부재중 응답 | 위임된 기술 질문은 근거를 남겨 원래 세션에서 이어지고, 사용자 전용 결정은 요청함에 남는다. 복귀 보고에서 두 경로를 추적한다. |
| 4. 오피스 보기와 자체 개선 | 역할 카드·캐릭터에서 작업 상세로 이동하고 Office 개선 후보를 검토 | 화면의 상태가 실행 기록과 일치한다. 별도 worktree에서 만든 후보는 회귀 테스트와 사람의 검토를 거쳐 승격하며 안정 버전의 실행 환경을 분리한다. |

첫 개발 범위는 **1단계**로 제안한다. 기존 AO-002의 관찰 화면과 엔진 기반 위에 로컬 작업 제어를 얹고, AO-003의 요청함과 AO-004의 자체 개선으로 이어간다. 원격 연결 방식, 엔진별 대화 프로토콜, 데스크톱 패키징은 각 단계의 검증 결과를 보고 결정한다.
