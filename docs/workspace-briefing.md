# Workspace 조정자 브리핑

작업실에 들어가면 응답할 요청, 검토할 후보, 진행·대기 중인 목표가 표시된다. 질문에서 원래 답변란으로 이동하거나 후보를 열어 변경과 검증 결과를 확인한다. 초상화는 해당 담당자와 대화하거나 추가 지시를 보낼 때 사용한다. 화면은 선택한 호스트의 저널을 읽는다. 연결이 끊기면 마지막으로 확인한 시각을 함께 표시한다.

## 세 작업을 함께 맡기기

1. 설정 저장 형식 변경(#41)을 맡긴다. 기존 파일을 변환할지 사용자 결정이 필요하다면 제품 질문이 열린다.
2. Windows 복원 오류(#42)를 맡길 때 작업별 옵션에서 #41과 원래 제품 질문을 선택한다. 기다릴 단계는 **구현**으로 둔다. 재현 가능한 기존 테스트를 실행하고, 필요하면 새 회귀 테스트를 원본 커밋에서 측정한 뒤 해당 결정까지 대기한다.
3. 댓글 문구 변경(#43)을 독립적으로 맡긴다. #41에 답하기 전에도 #43의 수정·검증·리뷰가 진행된다.
4. 브리핑에서 #41 질문을 열어 답한다. #42는 그 답변·출처·버전을 구현에 사용한다. 작업이 같은 제품 질문을 다시 보고해도 명시적으로 연결된 근거가 유효하고 질문이 일치할 때만 원래 답변을 재사용한다. 기술 질문이나 도구 권한은 이 방식으로 전파하지 않는다.

## 우선순위와 선행 조건

일반 의뢰에서는 조정 옵션을 비워 둬도 된다. 우선순위는 −9부터 9까지이고 기본값은 0이다. 준비된 대기 작업끼리 높은 순위부터 시작한다. 진행 중인 프로세스는 순서를 바꿔도 계속 실행된다. 파일 수정 목표에서 선택할 수 있는 경계는 시작·재현·구현·검증·리뷰이며 읽기 전용 작업은 시작 조건을 사용할 수 있다. 선행 목표의 성공적인 완료 또는 특정 제품 결정을 조건으로 선택한다.

직접 의뢰와 GitHub Issue 본문에는 선택적으로 다음 형식도 사용할 수 있다. `#41`은 같은 Workspace에 연결된 Issue를 뜻한다. GitHub를 통해 접수할 때는 동일 인스턴스·저장소로 한정한다. 번호가 모호하면 작업실에서 정확한 실행을 선택한다.

```markdown
## 작업 조정
- 우선순위: 3
- 변경 영역: 설정 저장 형식
- 선행: #41 | 구현 | 제품 결정 | 기존 설정을 자동 변환할까요? | 저장 형식 확정
```

완료를 기다릴 때는 `선행: #41 | 검증 | 완료 | 저장 형식 통합 확인`으로 지정한다. 질문을 원문으로 지정했을 때 같은 출처에서 여러 질문이 일치하면 원래 요청 ID를 선택한다. 중복된 조건과 순환 관계는 저장 전에 검사한다. 명시한 변경 영역이나 지시에 등장하는 파일·인터페이스가 겹치는 경우에는 비교 근거를 보여준다. 이 겹침만으로 대기 조건을 추가하지 않는다.

## 결정이 바뀌거나 실행이 중단될 때

조정 정보를 수정할 때는 확인한 버전을 함께 저장한다. 제품 질문의 답변을 정정하면 이전 답변과 그 답을 사용한 단계 기록이 보존된다. 이미 구현한 작업이 이전 결정을 사용했다면 이후 검증·리뷰에서 재작업이 필요하며, 남은 시도 예산 안에서 새 결정을 적용한다. 이전 결정에 의존한 후보는 과거 근거로 열어볼 수 있다. 취소된 선행 작업이나 더 이상 유효하지 않은 제품 결정 때문에 기다릴 때는 원래 목표와 연결을 확인한다.

대기 경계에서 작업자가 종료됐고 소유권·작업 트리·체크포인트가 확인되면 같은 실행에서 다음 단계부터 재개한다. 외부 작업이 진행 중이던 장애는 기존 복구 정책을 따른다. GitHub 접수, 하위 작업 동시 실행 한도, 후보의 독립 검토와 기존 병합·배포 승인은 각자의 정책을 사용한다.
