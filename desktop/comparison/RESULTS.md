# 설치형 데스크톱 실측

**두 OS 모두 Electron을 기본 앱으로 유지한다.** Rust 비교판의 설치 파일은 작았지만, Windows의 빈 작업실과 목표 작업실에서 전체 유휴 메모리 절감률은 같은 회차끼리 비교한 중앙값 기준 0.2~2.5%였다. 목표인 20%에 미달했다. Ubuntu의 목표 작업실에서는 전체 메모리와 유휴 CPU가 모두 증가했다. 이미 Studio와 WebView2가 있는 Windows PC에서 연결 전용 앱을 작게 설치하는 용도에는 Rust 비교판의 장점이 있다.

2026년 11월 21일, 이전 출시판 Electron 0.7.0과 Rust 비교판을 각각 **같은 최신 외부 Studio**에 연결했다. Windows의 Electron은 기존 출시 검증용 설치본을 사용했고, 설치된 `app.asar`의 SHA-256이 당시 출시 검증 기록과 일치했다. Electron 0.7.1의 변경은 설정 화면의 연결 주소·저널 표시와 번들 Studio 업데이트다.

두 앱 모두 1280×900 CSS 픽셀의 실제 창에서 같은 버튼과 입력란을 사용했다. 각 조건에서 앱마다 5회씩 실행하고 먼저 여는 앱을 회차마다 바꿨다. 첫 실행은 연결 정보만 미리 넣은 새 프로필, 재실행은 앱이 저장한 프로필을 사용했다. OS 파일 캐시는 유지했다. 목표 10개 중 8개 종료 기록과 검토 후보는 측정용으로 채웠다. 열 번째 목표는 실제 Studio 실행기와 모의 Codex 프로세스가 질문 답변을 기다렸다. [재현 방법](BENCHMARK.md)

준비 시간은 프로세스를 시작한 순간부터 빈 작업실의 등록 버튼 또는 목표 작업실의 질문·후보 버튼을 선택할 수 있을 때까지다. 두 앱에 똑같이 적용한 네이티브 창 크기 변경과 다시 그리는 시간도 포함했다. Ubuntu의 크기 변경 확인 구간 중앙값은 빈 작업실에서 Electron 74 ms·Rust 75 ms, 목표 작업실에서 69 ms·179 ms였다. 메모리는 Windows의 private commit과 Linux의 PSS로 측정했으므로 같은 운영체제 안에서 비교한다.

## Windows · NT 10.0.26300

목표 작업 중 창을 닫았다가 다시 열면 전체 메모리 중앙값은 Electron 490.2 MiB, Rust 483.1 MiB였다. 같은 회차끼리 계산한 Rust 절감률 중앙값은 1.3%였고, 창과 Studio만 포함하면 2.4%였다. 동일 목표의 브리핑을 다시 선택할 수 있을 때까지 걸린 시간은 Electron 914 ms, Rust 1,099 ms였다.

등록 입력란을 여는 시간은 Electron 28 ms·Rust 27 ms, 후보 패치가 표시되기까지 195 / 197 ms, 질문 입력란 복귀까지 166 / 173 ms였다. 각각 첫 실행과 재실행을 합한 앱별 10회 중앙값이다. Windows는 DPR 1.5를 사용했다. 크기 변경 확인 구간 중앙값은 빈 작업실 188 / 178 ms, 목표 작업실 250 / 180 ms였다.

목표 작업실에서 수집한 네 조건의 유휴 CPU 중앙값 범위는 Studio 1.5~2.7%, 실행기 0.5~1.1%, 모의 CLI 0.0%였다. 닫기 요청 후 3.0~3.3초경 40회 모두 창과 Chromium·WebView2 자손의 잔여 private commit은 0이었다. 목표 작업실에서 계속 실행된 Studio 71.3 MiB, 실행기 108.8 MiB, 모의 CLI 18.5 MiB는 닫기 후 중앙값이다. 테스트는 질문 대기에 들어오기 전에 끝났다. 각 앱에서 작업 중 닫은 뒤 5회 모두 같은 목표와 같은 작업 프로세스로 돌아왔다. Rust의 Windows 표준 오류에는 창 클래스 등록 해제 진단이 20회 남았고 앱의 정상 종료 코드는 모두 0이었다. ## Ubuntu 26.04 · WSL2

**이 환경에서는 Electron을 유지하는 편이 낫다.** 빈 작업실부터 Rust의 메모리가 더 컸다. 목표 10개가 있는 작업실을 다시 열면 작업 실행기와 CLI를 포함한 메모리는 Electron 523.1 MiB, Rust 743.9 MiB였다. 같은 회차끼리 비교한 중앙값으로 Rust가 42.4% 증가했다.

CPU는 한 논리 코어의 완전 점유를 100%로 표시했다. 화면 조작 스크립트가 끝난 뒤 답변 입력란에 포커스를 둔 유휴 9초 동안 Rust의 `WebKitWebProcess`가 중앙값 109.0%를 사용했다. Studio는 1.3~1.5%, 작업 실행기는 0.3~0.6%, 모의 CLI는 0.0%였다. 이 측정은 X11·Xvfb 1600×1000, DPR 1에서 진행했다. Rust의 진단에는 DRI3를 사용할 수 없다는 기록이 있어 물리 GPU 데스크톱에서의 결과는 별도 측정이 필요하다.

빈 작업실에서 등록 입력란을 여는 데 걸린 시간은 Electron 30 ms, Rust 85 ms였다. 브리핑에서 후보를 열고 변경 비교를 눌러 패치가 보이기까지 145 / 350 ms, 질문에서 원래 실행의 답변 입력란으로 돌아가기까지 84 / 184 ms였다. 각각 첫 실행과 재실행을 합한 앱별 10회 중앙값이다.

창을 닫은 지 약 3초 후 40회 모두 창 프로세스의 잔여 PSS는 0이었다. 목표가 있는 작업실에서 Studio 73.6 MiB, 실행기 101.5 MiB, 모의 CLI 10.8 MiB가 계속 실행됐다. 각 앱의 재실행 5회 모두 같은 저널·실행 ID·작업 프로세스를 확인했다. Linux의 WebKit 종료 진단은 제품 검증 기록에 별도로 남겼다. ### WSLg/XWayland 추가 관찰

동일한 바이너리를 WSLg의 실제 X11 소켓에서 열어 목표 작업실을 앱별로 한 번 열고 닫은 뒤 한 번 다시 열었다. 네 창 모두 1280×900 CSS 픽셀·DPR 1이었다. 셸 유휴 CPU는 첫 실행에서 Electron 2.0%·Rust 113.8%, 재실행에서 1.9%·122.9%였다. Rust의 `WebKitWebProcess`에서 각각 108.6%·117.5%를 관측했다. 전체 메모리는 첫 실행 479.2 / 704.9 MiB, 재실행 472.2 / 693.8 MiB였다. 이 경로에서도 DRI3 장치를 얻지 못했다는 진단이 남았다. 위 Xvfb의 조건별 5회 집계에서 이 추가 관찰은 제외했다. ## 설치 파일과 설치 후 용량

아래 수치는 MiB다. 설치판이 차지하는 일반 파일의 논리적 크기를 합산하고 하드 링크는 한 번만 계산했다. Rust에서 로컬 작업실도 사용하려면 외부 Studio가 필요하므로 Electron에 포함된 동일한 Python 런타임을 더한 용량을 함께 표시했다.

| 운영체제 | 설치 파일<br>Electron / Rust | 앱 설치 후<br>Electron / Rust | 같은 Studio 포함<br>Electron / Rust | Rust가 사용하는 공유 렌더러 |
|---|---:|---:|---:|---:|
| Windows | 151.1 / 2.2 | 492.5 / 9.8 | 492.5 / 145.3 | 이 PC에 설치된 WebView2 157.0.4341.60의 파일 690.5 |
| Ubuntu | 140.9 / 3.4 | 445.1 / 12.6 | 445.1 / 184.0 | WebKitGTK·JavaScriptCore 두 패키지 123.3 |

Windows에서는 WebView2가 이미 설치돼 있었다. 이 PC에서 Rust를 추가할 때 공유 렌더러 690.5 MiB를 다시 설치할 필요가 없었다.

실험용 패키지를 설치하기 전의 Ubuntu 호스트에는 Electron 0.4.0이 있었고 WebKitGTK 4.1과 JavaScriptCoreGTK 4.1은 없었다. 이 호스트에서 `apt-get -s`로 확인한 Rust의 추가 의존성은 기본 설정 기준 78개·다운로드 61.3 MiB·설치 후 약 214.1 MiB였다. 권장 패키지를 빼면 62개·57.5 MiB·202.0 MiB였다. 기본 설정의 추가 의존성과 같은 Studio까지 합치면 약 **398.0 MiB**이며, 이 안에 위 두 렌더러 패키지가 들어간다. 같은 호스트에서 Electron 0.7.0으로 업그레이드하는 데 추가 의존성은 0개였다. 실제로 설치된 앱 파일의 합계와 apt의 패키지 메타데이터 기반 추정치는 계산 방식이 다르다.
